## User Scenarios & Testing *(mandatory)*

### User Story 1 - 잘못된 선물을 막을 근거를 남긴다 (Priority: P1)

새로 가입한 사용자가 온보딩에서 **이미 있는 것**과 **필요 없는 것**을 대분류로 고른다. 저장한 뒤 자신의 취향 화면에서 방금 남긴 항목을 종류별로 확인한다.

**Why this priority**: 이것이 이 제품이 기존 위시리스트 서비스와 갈리는 지점이다. PRD Evidence는 "위시리스트 서비스는 존재하지만 이미 있는 것 / 필요 없는 것까지 함께 담는 서비스는 확인되지 않았다"고 적고 있다. 이 스토리 하나만 구현해도 "잘못된 선물을 걸러낼 근거 데이터"라는 제품 고유의 자산이 생긴다. 나머지 스토리는 이 자산을 두껍게 만드는 층이다.

**Independent Test**: 신규 사용자로 온보딩에 진입해 대분류를 골라 저장하고, 취향 화면에서 `이미 있는 것`과 `필요 없는 것`이 구분되어 표시되는지 확인한다. 다른 스토리 없이 완결된다.

**Acceptance Scenarios**:

1. **Given** 취향 항목이 하나도 없는 신규 사용자가 온보딩에 진입했을 때, **When** `필요 없는 것`으로 대분류 하나를 고르고 저장하면, **Then** 온보딩이 완료로 처리되고 그 항목이 취향 화면에 나타난다
2. **Given** 온보딩 화면에서, **When** 아무 대분류도 고르지 않고 저장을 시도하면, **Then** 저장되지 않고 최소 1건이 필요하다는 안내가 표시된다
3. **Given** 사용자가 `이미 있는 것`과 `필요 없는 것`을 각각 등록했을 때, **When** 취향 화면을 열면, **Then** 두 종류가 서로 다른 묶음으로 구분되어 보인다
4. **Given** 온보딩을 완료하지 않고 이탈한 사용자가, **When** 다시 접속하면, **Then** 중단된 온보딩을 이어서 진행할 수 있는 경로가 제시된다
5. **Given** 온보딩을 완료하지 않은 사용자가, **When** 취향 화면에 직접 진입을 시도하면, **Then** 취향 화면은 표시되지 않고 온보딩으로 유도된다
6. **Given** 로그인하지 않은 방문자가, **When** 인증이 필요한 화면에 접근하면, **Then** 로그인 화면으로 유도되고, 로그인에 성공하면 온보딩 완료 여부에 따라 온보딩 또는 취향 화면으로 이동한다 (FR-019)

---

### User Story 2 - 원하는 것을 남긴다 (Priority: P2)

사용자가 받고 싶은 선물을 **원하는 것**으로 등록한다.

**Why this priority**: 선물의 정답을 직접 제시하는 층이다. P1이 "무엇을 주지 말아야 하는가"를 담는다면 이 스토리는 "무엇을 주면 되는가"를 담는다. P1 없이도 독립적으로 동작하지만, P1이 만드는 차별점보다는 뒤에 둔다.

**Independent Test**: 취향 화면에서 `원하는 것`을 등록하고, 저장 후 목록에 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 취향 화면에서, **When** `원하는 것`으로 대분류를 골라 저장하면, **Then** 해당 항목이 `원하는 것` 묶음에 표시된다
2. **Given** 사용자가 `원하는 것`을 하나도 등록하지 않았을 때, **When** 취향 화면을 열면, **Then** 온보딩 완료 상태가 유지되고 `원하는 것`이 비어 있음이 안내된다 — 이 항목은 필수가 아니다

---

### User Story 3 - 취향을 상세하게 만든다 (Priority: P3)

사용자가 대분류에 **상세**를 덧붙이거나(예: 대분류 `텀블러`에 상세 `스타벅스 텀블러`), 자유 입력으로 **취향 서술**을 남긴다.

**Why this priority**: PRD Risks R2가 지목한 위험 — "맞춤 취향이 대분류에서 멈추고 상세·서술이 비면 평범한 위시리스트로 회귀한다" — 을 직접 겨냥하는 층이다. 제품의 성패를 가르지만, 앞선 두 스토리가 없으면 붙일 자리가 없으므로 뒤에 온다.

**Independent Test**: 이미 등록한 항목에 상세를 덧붙이고, 취향 서술을 저장한 뒤, 둘 다 화면에 반영되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 대분류만 지정된 항목이 있을 때, **When** 상세를 덧붙여 저장하면, **Then** 대분류와 상세가 함께 표시된다
2. **Given** 항목을 등록하는 중에, **When** 상세를 비운 채 저장하면, **Then** 대분류만으로 정상 저장된다 — 상세는 강제되지 않는다
3. **Given** 취향 서술이 비어 있을 때, **When** 자유 입력으로 서술을 저장하면, **Then** 취향 화면에 서술이 표시된다
4. **Given** 취향 서술을 저장하지 않았을 때, **When** 취향 화면을 열면, **Then** 서술 없이도 화면이 정상 동작한다

---

### User Story 4 - 남긴 취향을 고치고 지운다 (Priority: P4)

사용자가 이미 등록한 취향 항목의 내용을 수정하거나 목록에서 삭제한다.

**Why this priority**: 시연만 놓고 보면 P1~P3로 충분하지만, 실사용에서는 오입력 복구와 상황 변화 반영이 없으면 데이터가 금세 신뢰를 잃는다. 취향 데이터의 정확도가 이 제품의 자산이므로 마일스톤 1을 벗어나기 전에 반드시 포함한다.

**Independent Test**: 등록된 항목의 상세를 수정하고, 다른 항목을 삭제한 뒤, 두 변경이 취향 화면에 반영되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 등록된 취향 항목이 있을 때, **When** 상세나 종류를 수정해 저장하면, **Then** 변경 내용이 즉시 반영된다
2. **Given** 등록된 취향 항목이 있을 때, **When** 삭제를 실행하면, **Then** 삭제 전 확인을 거친 뒤 목록에서 사라지며 복구되지 않는다
3. **Given** `이미 있는 것`/`필요 없는 것` 항목이 정확히 1건뿐일 때, **When** 그 항목을 삭제하면, **Then** 온보딩 미완료 상태로 되돌아가고 재등록을 안내한다

---

### Edge Cases

- 사용자가 같은 대분류를 `원하는 것`과 `필요 없는 것`에 동시에 등록하려 하면 어떻게 되는가 — 모순이므로 저장을 막고, 어떤 기존 항목과 충돌하는지 알린다
- 동일한 (종류, 대분류, 상세) 조합을 두 번 등록하려 하면 어떻게 되는가 — 중복 저장을 막고 기존 항목을 안내한다
- 카테고리 목록에 사용자가 원하는 대분류가 없으면 어떻게 되는가 — 가장 가까운 대분류를 고르고 상세에 자유 입력으로 적는다
- 특정 종류의 취향 항목이 상한(100건)에 도달한 상태에서 추가 등록을 시도하면 어떻게 되는가 — 저장을 막고 현재 개수와 상한을 알린다 (FR-020)
- 저장 중 통신이 끊기면 어떻게 되는가 — 저장 실패를 사용자에게 알리고 입력 내용을 잃지 않는다
- 온보딩 필수 항목을 채우기 전에 앱의 다른 영역으로 이동하려 하면 어떻게 되는가 — **취향 데이터를 필요로 하는 영역만 차단하고 온보딩으로 유도한다.** 그 외 영역은 열어 둔다 (FR-018)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 취향 프로필은 사용자 1인당 정확히 하나 존재한다
- **FR-002**: 사용자는 **자신의** 취향 프로필만 작성·수정할 수 있다. 타인의 취향을 대신 등록하는 경로를 제공하지 않는다
- **FR-003**: 모든 취향 항목은 `원하는 것` · `이미 있는 것` · `필요 없는 것` 중 정확히 하나의 종류를 갖는다. `이미 있는 것`과 `필요 없는 것`은 별개 종류로 구분되어 표시된다
- **FR-004**: 모든 취향 항목은 미리 정의된 카테고리 목록에서 고른 대분류를 반드시 갖는다. 대분류를 자유 텍스트로 입력받지 않는다
- **FR-005**: 시스템은 계층 없는 평면 카테고리 목록을 제공하며, 목록은 30~50개 항목으로 구성한다. 묶음(`group`)은 **화면 표시용 이름표**이며 선택 대상이 아니다 — 취향 항목은 묶음이 아니라 대분류를 참조하므로 데이터 구조는 평면을 유지한다 (categories.md §3)
- **FR-006**: 상세 지정은 선택이다. 시스템은 상세 입력을 강제하지 않는다
- **FR-007**: 취향 서술은 선택이며 자유 입력을 허용한다
- **FR-008**: 시스템은 `이미 있는 것` 또는 `필요 없는 것` 항목이 1건 이상 등록되었을 때 온보딩을 완료로 판정한다
- **FR-009**: 시스템은 온보딩 미완료 사용자에게 중단 지점부터 이어서 진행할 수 있는 경로를 제공한다
- **FR-010**: 시스템은 같은 대분류에 대해 상세 없는 `원하는 것` 항목과 `필요 없는 것` 항목이 동시에 존재하는 것을 막고, 어떤 항목과 충돌하는지 사용자에게 알린다
- **FR-011**: 시스템은 동일한 (종류, 대분류, 상세) 조합의 중복 등록을 막는다
- **FR-012**: 사용자는 자신의 취향 항목 전체를 종류별로 묶어 조회할 수 있다
- **FR-013**: 사용자는 등록한 취향 항목을 수정할 수 있다
- **FR-014**: 사용자는 등록한 취향 항목을 삭제할 수 있다. 삭제는 확인 절차를 거치며 복구되지 않는다
- **FR-015**: 시스템은 저장된 데이터만으로 상세 작성률과 취향 서술 작성률을 집계할 수 있어야 한다. 이 집계는 별도의 사용자 행동 이벤트 수집에 의존하지 않는다
- **FR-016**: 시스템은 저장 실패 시 사용자에게 실패를 알리고 입력 내용을 보존한다
- **FR-017**: 모든 화면은 모바일을 기준으로 설계하며 태블릿·데스크톱에서도 동작한다
- **FR-018**: 시스템은 온보딩 미완료 사용자가 **취향 데이터를 필요로 하는 영역**에 진입하려 할 때 온보딩으로 유도한다. 취향 데이터와 무관한 영역은 차단하지 않는다
- **FR-019**: 시스템은 **소셜 로그인 1종**을 통한 로그인 화면을 제공한다. 미인증 사용자가 인증이 필요한 영역에 진입하려 하면 이 화면으로 유도한다. 로그인 성공 후에는 온보딩 완료 여부에 따라 FR-018의 판정을 따른다
- **FR-020**: 시스템은 한 프로필의 취향 항목 수를 **종류별 100건**으로 제한한다. 상한에 도달한 종류에 추가 등록을 시도하면 저장을 막고 현재 개수와 상한을 안내한다

### Key Entities *(include if feature involves data)*

- **취향 프로필**: 한 사용자의 취향 전체를 묶는 단위. 취향 서술과 온보딩 완료 여부를 갖는다. 사용자와 1:1로 대응한다
- **취향 항목**: 취향 프로필에 속하는 개별 기록. 종류(`원하는 것`/`이미 있는 것`/`필요 없는 것`), 대분류, 선택적 상세로 구성된다. 부연 메모는 M1에서 다루지 않는다 — 상세 및 취향 서술과 용도가 겹친다
- **카테고리**: 대분류의 마스터 목록. 취향 항목이 참조하며, 이후 마일스톤에서 상품도 같은 목록을 참조한다. 이 공유가 "잘못된 선물 걸러내기"의 전제다
- **사용자**: 취향 프로필의 소유자이자 유일한 작성자

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 신규 사용자가 온보딩 필수 항목을 **3분 이내**에 완료한다
- **SC-002**: 온보딩에 진입한 사용자의 **80% 이상**이 `이미 있는 것` 또는 `필요 없는 것`을 1건 이상 등록하고 완료에 도달한다
- **SC-003**: 등록·수정·삭제한 취향 항목이 취향 화면 재조회 시 **100%** 반영된다
- **SC-004**: 마일스톤 1 완료 시점에 **상세 작성률**(상세를 1건 이상 지정한 사용자 비율)과 **취향 서술 작성률**을 즉시 산출할 수 있다. 목표 수치는 근거 확보 전까지 `TBD`로 둔다 — PRD Risks R2 검증
- **SC-005**: 모순되는 취향 항목(같은 대분류의 `원하는 것`과 `필요 없는 것`)이 저장되는 사례가 **0건**이다
- **SC-006**: 폭 360px 화면에서 가로 스크롤 없이 모든 기능을 사용할 수 있다
- **SC-007**: **구현에 참여하지 않은 외부 5명**에게 취향 화면을 보여주고 `이미 있는 것`과 `필요 없는 것`을 구분할 수 있는지 물었을 때 **4명 이상**이 성공한다. 마일스톤 1 완료 직전 1회 실시하고 결과를 숫자로 기록한다. 평가자를 팀 밖에서 구하는 이유는 인원수 때문이 아니라 **편향** 때문이다 — 화면을 만든 사람은 자기 화면을 항상 구분한다

## Assumptions

- **인증은 소셜 로그인 1종으로 하며, 최소 로그인 화면이 이 마일스톤에 포함된다** (FR-019). 어떤 제공자를 쓸지와 세션 전략은 계획 단계에서 확정한다. 로그인 화면 없이는 US1~US4의 수용 시나리오를 하나도 실행할 수 없으므로 범위 밖으로 둘 수 없다
- **데이터 저장 기술은 이 스펙에서 정하지 않는다.** 계획 단계에서 확정한다
- 카테고리 목록의 실제 항목 구성(어떤 30~50개인가)은 별도 산출물로 확정한다. 이 스펙은 개수 범위와 평면 구조만 규정한다
- **취향 항목 수는 종류별 100건으로 제한한다** (FR-020). 상한을 두는 이유는 화면이 전체를 한 번에 로드하기 때문이다 — 상한이 없으면 목록 조회 방식을 페이지네이션으로 바꿔야 하고, 그러면 조회 계약과 화면과 테스트가 함께 바뀐다. 100건은 실사용에서 도달하기 어려운 수치이면서 전량 로드가 안전한 범위다
- `원하는 것` 항목은 이 마일스톤에서 텍스트로만 기록한다. 상품 카탈로그와의 연결은 마일스톤 3에서 다룬다
- 삭제된 취향 항목의 복구 기능은 제공하지 않는다. 취향 항목은 되돌릴 이유가 없는 데이터로 간주한다
- **온보딩 미완료 사용자의 접근은 취향 데이터가 필요한 영역만 차단한다** (FR-018). 전면 차단은 가입 직후 이탈 위험을 키우고, 무차단은 취향이 빈 채로 링크를 공유하는 상황을 만든다 — 둘 다 PRD Risks R1(콜드스타트)의 서로 다른 얼굴이다. 이 선택은 마일스톤 2~4가 붙어도 규칙을 다시 정하지 않아도 되는 유일한 안이다

## Out of Scope

- 친구 관계, 취향 공유 링크, 열람 권한 — 마일스톤 2
- 상품 카탈로그, 선물 요청, 승인·대안 제시, 결제 — 마일스톤 3
- 펀딩 — 마일스톤 4
- 친구 그룹별 차등 공개, 취향 조회 로그, 친구에 대한 개인 메모 — 전부 Future
- 타인의 취향 대리 등록 — 도메인 모델 D1에서 제외 확정
- **계정 탈퇴와 그에 따른 취향 데이터 처리** — 탈퇴 화면, 보관 기간, 복구 가능 여부를 M1에서 정하지 않는다.
  `data-model.md`의 `onDelete: Cascade`(계정 삭제 시 취향 함께 삭제)는 **잠정 결정**이며, 탈퇴 기능을 실제로 다루는 시점에 재검토한다.
  취향 데이터에는 알러지·사이즈가 포함되어 민감정보에 해당하므로(PRD Risks R9), 탈퇴 정책은 그 마일스톤에서 명시적으로 결정해야 한다
