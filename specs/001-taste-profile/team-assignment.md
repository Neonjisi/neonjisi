> 🚨 **T010이 이 프로젝트에서 가장 놓치기 쉬운 태스크다.**
>
> PostgreSQL은 유니크 인덱스에서 **NULL을 서로 다른 값으로 취급**한다. 그래서 그냥
> 유니크를 걸면, 상세를 안 적은 항목(= 가장 흔한 형태)이 **무제한 중복 등록된다.**
> 화면상으로는 완전히 정상으로 보여서 나중에야 발견된다.
>
> Prisma 스키마 문법으로는 표현할 수 없어서 이렇게 한다:
> ```bash
> npx prisma migrate dev --create-only --name taste_item_unique_nulls_not_distinct
> ```
> 생성된 SQL 파일을 열어 직접 넣는다:
> ```sql
> ALTER TABLE "TasteItem"
>   ADD CONSTRAINT "TasteItem_profile_kind_category_detail_key"
>   UNIQUE NULLS NOT DISTINCT ("profileId", "kind", "categoryId", "detail");
> ```
> **T011이 이게 실제로 걸렸는지 확인하는 유일한 장치다.** 같이 해야 의미가 있다.

> **T008~T011은 순서대로, 혼자.** 마이그레이션 순서가 어긋나면 팀 전원의 로컬 DB가 갈라진다.

> 평범한 위시리스트로 회귀한다. 문구가 이 마일스톤의 성패에 직접 닿아 있다.

#### ③ T059 — quickstart 전체 수동 검증 (Phase 7)

`quickstart.md`의 V1~V7을 순서대로 직접 밟는다. 개발자가 아닌 사람이 하는 게 낫다 —
만든 사람은 자기가 아는 경로로만 클릭한다.

#### ④ T060 — SC-007 사용자 확인 (Phase 7)

**구현에 참여하지 않은 외부 5명**에게 취향 화면을 보여주고 묻는다:

> "여기서 `이미 있는 것`과 `필요 없는 것`을 구분할 수 있나요?"

**5명 중 4명 이상 성공**이 기준. 결과를 숫자로 기록한다.

> ⚠️ **팀원은 평가자가 될 수 없다.** 인원수 때문이 아니라 편향 때문이다 — 화면을 만든
> 사람은 자기 화면을 항상 구분한다. 같은 수업 수강생 정도면 충분하다.

#### ⑤ 상시 — 다음 마일스톤 준비 (Phase 5~6 중)

M1 개발이 병행 구간에 들어가면 S의 손이 빈다. 그때 **마일스톤 2(친구에게 취향이 전달된다)**
스펙 초안을 시작하면 M1 종료와 동시에 M2로 넘어갈 수 있다.

## 3. 왜 이렇게 나눴나 — 충돌 지도

US2·US3·US4를 그냥 세 명에게 나눠 주면 **모든 쌍이 정확히 한 파일씩 충돌한다.**

| 파일 | 건드리는 스토리 | 충돌 쌍 |
|---|---|---|
| `app/taste/actions.ts` | US3(T043) · US4(T049·T050) | US3 ↔ US4 |
| `components/taste/taste-item-list.tsx` | US2(T038) · US4(T051) | US2 ↔ US4 |
| `app/taste/page.tsx` | US2(T037) · US3(T045) | US2 ↔ US3 |

**해법 두 가지**:

1. **`actions.ts`를 J가 혼자 소유한다** → US3 ↔ US4 충돌이 사라진다
2. **US2를 D가 먼저 단독으로 끝낸다** → 나머지 두 충돌이 시간차로 해소된다

결과적으로 Phase 5·6을 동시에 진행해도 같은 파일을 두 사람이 만지는 일이 없다.

## 4. 협업 규칙

### 지켜야 할 것

| 규칙 | 이유 |
|---|---|
| **`lib/prisma.ts`를 화면·액션에서 직접 import 금지** | 반드시 `lib/dal/`을 거친다. 이 프로젝트에는 DB 레벨 2차 방어선이 없어서 DAL이 유일한 접근 제어 지점이다. T023의 ESLint 규칙이 이걸 막는다 |
| **테스트를 먼저 쓴다** | 각 스토리의 테스트 태스크가 구현 태스크보다 앞 번호다. 순서를 바꾸지 않는다 |
| **`.env.local`은 절대 커밋하지 않는다** | 각자 로컬에만 |
| **마이그레이션은 J만 만든다** | 여러 명이 만들면 순서가 갈려 팀 전원의 DB가 어긋난다 |
| **Phase 완료 시 커밋** | 각 Phase 끝의 Checkpoint에서 동작을 확인하고 커밋 |

### Next.js 16 주의

- **`middleware.ts`가 아니라 `proxy.ts`다.** 16에서 이름이 바뀌었다
- **비동기 서버 컴포넌트는 단위 테스트가 어렵다.** 화면 검증은 Playwright(E2E)로 한다
