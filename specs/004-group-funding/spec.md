# Feature Specification: 고가 선물을 여럿이 함께 준비한다 (마일스톤 4)

**Feature Branch**: `004-group-funding`

**Created**: 2026-08-31

**Status**: Draft — **M3 완료 후 clarify → plan → tasks를 돌린다** (분담표 §7: "M3가 끝나야
해상도가 올라간다." 펀딩은 M3의 `Product`·`PaymentMethod`·`Payment`·알림 인프라를 전부 재사용한다)

**Input**: User description: "M4 — 고가 선물을 여럿이 함께 준비한다. 주최자가 상품·목표 금액·최소 달성선·마감일로 펀딩을 열고, 친구들이 선결제로 참여한다. 마감 시 달성선 기준으로 성사·미달이 갈리고, 미달이면 전액 환불, 성사인데 목표에 모자라면 주최자 차액 자동 결제. 목표를 채우면 조기 성사."

---

## 이 기능이 무엇인가

M3가 1:1 선물을 완성했다. M4는 **혼자 사기 부담스러운 선물을 여럿이 나눠 사는** 층이다 —
주최자가 펀딩을 열고, 친구들이 선결제로 보태고, 달성선을 넘으면 성사된다.

세 가지가 이 마일스톤의 정체성이다.

1. **선결제라서 모인 돈이 곧 확정된 돈이다** (확정 결정 5-1). 결제를 성사 판정 뒤로 미루면
   판정 후에 총액이 무너질 수 있다. 대가로 미달·취소 시 **전액 환불**이 필수 경로가 된다.
2. **개설자 = 수령자면 차액 개념이 사라진다** (확정 결정 5-5). 최소 달성선이 목표 금액으로
   강제되어, "자기 선물의 차액을 자기가 내는" 모순(PRD R3)이 구조적으로 소멸한다.
3. **총액의 정의가 두 곳에서 다르다.** 성사 판정은 결제 완료분만, 잔여 캡 계산은
   예약분+결제분이다. 이 둘을 섞으면 조용히 깨진다 — 결제 안 될 돈으로 성사를 선언하거나,
   동시 참여가 목표를 넘긴다.

M3와 마찬가지로 돈이 오가고, 이번에는 **주최자·수령자·참여자 3주체**다. 검증에 계정 3개가
필요하다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 펀딩을 연다 (Priority: P1)

주최자가 상품을 고르고, 대상(나에게/친구에게)을 정하고, 목표 금액·최소 달성선·마감일을
입력한다. **친구에게 여는 경우** 마지막 스텝에서 "미달분은 내 카드로 자동 결제된다"에
동의한다(최대 부담액을 숫자로). **나에게 여는 경우** 달성선 입력이 목표 금액으로 잠기고
차액 동의 스텝이 통째로 생략된다.

**Why this priority**: 펀딩이 존재해야 참여도 정산도 있다. 개설 시점의 동의가 차액 자동
결제(US3)의 권한 위임 장치다.

**Independent Test**: 계정 1~2개로 두 분기(나에게/친구에게)의 개설 완료와 저장 값 검증.
참여 없이 성립.

**Acceptance Scenarios**:

1. **Given** 주최자가 "친구에게"를 골랐다, **When** 3스텝을 밟는다, **Then** 목표·달성선·
   마감일 입력 → 차액 동의(최대 부담액 **숫자** 명시 · 결제수단 필수 · 체크 전 버튼 비활성) →
   펀딩이 열린다
2. **Given** 주최자가 "나에게"를 골랐다, **When** 개설 플로우를 밟는다, **Then** 달성선
   입력이 **숨겨지지 않고 잠긴 채** 목표 금액과 동일하게 표시되고("내가 받는 선물이라 목표를
   다 채워야 성사됩니다"), 차액 동의 스텝 없이 2스텝으로 끝난다
3. **Given** 달성선을 목표보다 크게 입력했다, **Then** "최소 달성선은 목표 금액보다 클 수
   없어요" — 저장 계층에서도 거부된다
4. **Given** 마감일이 현재 이전이다, **Then** 거부된다. 목표 금액 < 상품 가격은 **경고만** —
   막지 않는다
5. **Given** 주최자에게 활성 결제수단이 없다("친구에게" 분기), **Then** 등록 화면 강제 진입
   후 복귀 (M3 US2 재사용)
6. **Given** 개설이 완료됐다, **Then** 수령자 표시명·상품 정보가 펀딩 안에 스냅샷되고,
   동의 시각·문구 버전이 기록된다

### User Story 2 - 선결제로 참여한다 (Priority: P1)

친구가 펀딩 상세에서 진행 상황(모인 금액·달성선·남은 금액·마감)을 보고, 잔여 금액 이하로
금액을 정해 **결제와 동시에** 참여한다. 참여 전에 "수령자와 주최자에게 금액이 공개됩니다"와
"달성선에 못 미치면 전액 환불됩니다" 두 고지를 본다.

**Why this priority**: 동시성 최대 위험 구간 — 두 명이 동시에 남은 금액을 참여하면 목표를
넘는다. 예약(잔여 잠금) → 결제 → 확정의 2단계가 이것을 막는다.

**Independent Test**: US1로 만든 펀딩에 계정 2~3개가 참여해 금액 누적·잔여 캡·동시 참여를
검증. 정산 없이 성립.

**Acceptance Scenarios**:

1. **Given** 진행 중 펀딩 상세, **Then** 진행바(**결제 완료분만**) · 달성선 도달 표시 ·
   남은 금액(**예약+결제분 기준**) · 예약 중 금액이 있으면 "결제 중 N원" 줄 · D-day가 보인다
2. **Given** 참여 화면, **Then** 고지 2종("공개됩니다" · "환불됩니다")이 나란히 보이고,
   빠른 선택 칩의 마지막은 항상 "전액"이다
3. **Given** 잔여 금액을 넘는 입력, **Then** "남은 금액은 N원이에요" — 버튼 비활성.
   서버에서도 예약 시점 잔여 확인으로 거부된다
4. **Given** 두 참여자가 동시에 잔여 금액 전액을 시도한다, **Then** 한 명만 예약에 성공하고
   다른 한 명은 "방금 목표를 채웠어요"를 본다 — **합계가 목표를 넘는 일이 없다**
5. **Given** 참여 결제가 성공했다, **Then** 참여 완료 화면(모인·남은 금액 갱신)과
   주최자 알림. 실패하면 **예약이 해제**되고 재시도를 안내한다
6. **Given** 예약 후 결제가 오래 걸린다, **When** 예약 유효 시간이 지난다, **Then** 예약이
   만료되어 잔여 금액이 풀린다 — 배치 없이 조회 시점 지연 평가
7. **Given** 이미 참여한 사람, **Then** **추가 참여가 허용**된다(별도 참여 건).
   참여 취소는 **예약 상태에서만** 가능하다
8. **Given** 목표가 다 찼다(잔액 0), **Then** 참여 버튼이 비활성이다
9. **Given** 지분 공개 규칙, **Then** 주최자·수령자는 **전원 이름+금액**, 일반 참여자는
   이름 나열+**자기 금액만**, 비참여 친구는 이름만 보인다

### User Story 3 - 마감이 성사·미달을 가르고 돈이 정리된다 (Priority: P1)

마감 시점에 **결제 완료분 합계**가 달성선을 넘으면 성사, 못 넘으면 미달이다. 성사인데 목표에
모자라면 주최자 카드로 **차액이 자동 결제**되고 반드시 고지된다. 미달·취소면 모든 결제 완료
참여 건이 **전액 환불**된다. 결제 완료분이 목표에 도달하면 마감 전이라도 **조기 성사**하고
참여를 마감한다.

**Why this priority**: **마일스톤 완료 판정이 여기다** — "달성선 기준으로 성사·취소가 갈리고,
미달 시 전액 환불된다. 차액 자동 결제가 동작한다."

**Independent Test**: US1·US2로 만든 상태에서 마감·조기 성사·미달·취소 네 갈래를 각각 만들어
상태 전이·환불·차액 결제·알림을 검증.

**Acceptance Scenarios**:

1. **Given** 마감 시점에 결제 완료 합계 ≥ 달성선, **Then** 성사 — 참여자·수령자에게 알림
2. **Given** 성사인데 합계 < 목표, **Then** 주최자 카드로 `목표 − 합계`가 자동 결제되고
   **`funding_organizer_topup` 고지가 반드시 간다** — "동의를 받았어도 고지는 별개다"
3. **Given** 결제 완료 합계 = 목표(마감 전), **Then** **조기 성사** — 참여가 마감된다
4. **Given** 마감 시점에 합계 < 달성선, **Then** 미달 — 모든 결제 완료 참여 건이 전액
   환불되고 참여자에게 `funding_failed_refunded` 알림이 간다 (돈이 오갔으므로 필수)
5. **Given** 주최자가 진행 중 펀딩을 취소한다, **Then** 전 참여 건 환불. 미달과 취소는
   **다른 문구**로 구분된다 — "달성선에 못 미쳤어요" vs "주최자가 펀딩을 취소했어요"
6. **Given** 성사 판정, **Then** 판정 합계에 **예약 중 금액은 절대 포함되지 않는다** —
   결제되지 않을 수도 있는 돈으로 성사를 선언하지 않는다
7. **Given** 환불이 진행된다, **Then** 환불 진행 상황은 참여 건 단위로 남는다 — 펀딩 자체는
   미달/취소 상태를 유지한다 (환불 상태를 따로 두지 않는다)

### User Story 4 - 결과와 내역이 보이고 홈에 모인다 (Priority: P2)

종료된 펀딩의 결과 화면(성사/차액 발생 주최자/미달 3변형), 펀딩 내역(내가 연 것/참여한 것),
그리고 M3에서 숨겨뒀던 홈의 진행 중 펀딩 섹션이 열린다.

**Why this priority**: US1~US3만으로 돈의 흐름은 완결된다. 결과·내역·홈은 그것을 보이게
하는 층이다.

**Independent Test**: 종료 상태별 펀딩 데이터로 결과 3변형·내역 탭·홈 섹션을 검증.

**Acceptance Scenarios**:

1. **Given** 성사(정산 완료), **Then** 참여자·수령자에게 상품·참여자 수·내 참여 금액이 보인다
2. **Given** 차액이 발생한 주최자, **Then** 모인 금액·목표·차액과 "차액 N원이 OO 카드로
   결제되었습니다"가 보인다
3. **Given** 미달, **Then** 모인 금액·달성선과 "참여하신 N원은 전액 환불됩니다"가 보인다
4. **Given** 펀딩 내역, **Then** 내가 연 것/참여한 것 탭, 진행 중/끝난 펀딩 구분,
   끝난 건의 결과 라벨(성사·미달 취소·환불 완료)이 보인다
5. **Given** M4가 열렸다, **Then** 홈의 진행 중 펀딩 섹션이 활성화된다 — 내가 주최·참여·수령
   중인 `open` 펀딩이 마감 임박순으로 보인다
6. **Given** 게이지 애니메이션, **Then** 진입 시 400ms 1회만 — 카운트다운·금액 숫자에 모션
   금지 (화면 명세 §4.7)

### Edge Cases

- **첫 참여자가 "전액" 칩으로 펀딩을 끝낸다** → 막지 않는다 — 정책이 1인 상한을 두지 않았다
  (PRD). 잔여 금액 표시와 확인 단계가 완화책의 전부다 (R4)
- **참여 진입 중 잔액이 소진된다** → "방금 목표를 채웠어요" → 상세로 복귀
- **예약만 하고 결제가 안 끝난 참여가 쌓인다** → 예약 유효 시간이 지나면 지연 평가로 해제 —
  잔여 금액이 영구히 잠기지 않는다
- **마감 직전 동시 참여** → 예약 시점의 잔여 확인이 잠금 안에서 일어나므로 초과가 없다.
  성사 판정은 결제 완료분만 본다
- **관계 해제 후 진행 중 펀딩** → 수령자 표시명·상품 스냅샷만으로 계속 렌더된다(M3와 같은
  원칙). 취향 접근은 차단
- **차액 자동 결제가 실패한다** → M3의 결제 실패 경로(재시도)를 재사용한다. 상세 정책은
  M4 clarify에서 닫는다 (아래 열린 항목)
- **환불 문구** — 미달과 주최자 취소를 같은 문구로 뭉개지 않는다. 법·감정 양쪽이 걸린
  문구(고지 2종 포함)는 화면 구현 전에 확정한다 (S)

## Requirements *(mandatory)*

### Functional Requirements

#### 개설

- **FR-001**: 주최자는 상품·대상(나에게/친구에게)·목표 금액·최소 달성선·마감일로 펀딩을
  열 수 있어야 한다. 수령자는 활성 친구(또는 본인)만 가능하다
- **FR-002**: 최소 달성선은 목표 금액 이하여야 한다 — 화면과 저장 계층 양쪽에서 강제
- **FR-003**: **개설자 = 수령자이면 최소 달성선이 목표 금액으로 강제**되어야 한다(저장 계층
  포함). 화면은 입력을 숨기지 않고 잠그고 이유를 설명한다
- **FR-004**: 개설자 ≠ 수령자이면 개설 확정 전에 **차액 부담 동의**를 받아야 한다 — 최대
  부담액(목표 − 달성선)을 **숫자로** 명시, 활성 결제수단 필수, 동의 시각·문구 버전 기록.
  문구 수정 시 버전 업 (M3 FR-015와 같은 규칙)
- **FR-005**: 펀딩은 생성 시점에 상품 정보와 수령자 표시명을 스냅샷해야 한다 (M3 FR-016과
  같은 원칙)

#### 참여 — 선결제 · 2단계 예약

- **FR-006**: 참여는 **선결제**다 — 결제 완료가 곧 참여 확정이다. 1인 참여 상한은 없다
- **FR-007**: 참여 금액은 잔여 금액을 넘을 수 없어야 한다. 잔여 확인과 예약은 **원자적으로**
  일어나야 하며, 동시 참여의 합계가 목표를 초과할 수 없다
- **FR-008**: 참여는 예약 → 결제 → 확정의 2단계여야 한다. 결제 실패·시간 초과 시 예약이
  해제되어 잔여 금액이 풀린다. 예약 만료는 배치 없이 지연 평가로 판정한다
- **FR-009**: **총액 계산은 정확히 두 가지 정의를 쓴다** — 성사·미달 판정은 결제 완료분만,
  잔여 캡은 예약분+결제분. 두 합산은 단일 모듈에 모으고, 화면 표기도 이를 반영한다
  (진행바 = 결제 완료분 · "결제 중 N원" 별도 줄)
- **FR-010**: 참여 확정 전에 두 고지를 보여야 한다 — ① 수령자·주최자에게 금액이 공개된다
  ② 달성선 미달 시 전액 환불된다
- **FR-011**: 이미 참여한 사람의 추가 참여를 허용한다(별도 참여 건). 참여 취소는 예약
  상태에서만 가능하다
- **FR-012**: 참여 확정 시 주최자에게 알림이 가야 한다

#### 지분 공개

- **FR-013**: 참여 내역 공개는 3단계다 — 주최자·수령자는 전원 이름+금액, 참여자는 이름
  나열+자기 금액만, 비참여자는 이름만. 참여자끼리 서로의 금액을 볼 수 없다 (PRD R5)

#### 정산 — 성사 · 미달 · 환불 · 차액

- **FR-014**: 마감 시점에 결제 완료 합계 ≥ 달성선이면 성사, 미만이면 미달이다
- **FR-015**: 결제 완료 합계가 목표에 도달하면 마감 전이라도 **조기 성사**하고 참여를 마감한다
- **FR-016**: 성사 시 합계 < 목표이면 주최자 결제수단으로 차액을 자동 결제하고, **결제 후
  반드시 고지**해야 한다 — 동의와 고지는 별개다
- **FR-017**: 미달·주최자 취소 시 모든 결제 완료 참여 건을 **전액 환불**하고 참여자에게
  고지해야 한다 — 돈이 오갔으므로 누락될 수 없다
- **FR-018**: 미달과 주최자 취소는 상태와 문구 양쪽에서 구분되어야 한다. 환불 진행 상황은
  참여 건 단위로 기록하며 펀딩 자체에 환불 상태를 두지 않는다
- **FR-019**: 펀딩 상태 전이는 단일 모듈의 허용 화살표만 따라야 한다 — 열림 → 성사 →
  정산 완료 / 열림 → 미달 / 열림 → 취소 (M3 FR과 같은 원칙)

#### 알림

- **FR-020**: funding 알림 4종이 추가되어야 한다 — 참여 발생(주최자) · 성사(참여자·수령자) ·
  미달 환불(참여자) · 차액 결제(주최자). 각각 문구와 이동 목적지를 가진다

#### 결과 · 내역 · 홈

- **FR-021**: 종료 결과 화면은 3변형이다 — 성사(참여자·수령자) / 차액 발생(주최자) / 미달
- **FR-022**: 펀딩 내역은 내가 연 것/참여한 것, 진행 중/끝난 펀딩을 구분해야 한다
- **FR-023**: 홈의 진행 중 펀딩 섹션이 활성화되어야 한다 — 내가 주최·참여·수령 중인 열린
  펀딩, 마감 임박순

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 동시 참여를 아무리 넣어도 예약+결제 합계가 목표 금액을 초과한 펀딩이 0건이다
- **SC-002**: 성사 판정에 예약 중 금액이 포함된 사례가 0건이다 — 판정은 결제 완료분만
- **SC-003**: 미달·취소 펀딩의 결제 완료 참여 건 환불 누락이 0건이고, 참여자 전원이 고지를
  받는다
- **SC-004**: 차액 자동 결제 후 주최자 고지 누락이 0건이다
- **SC-005**: 개설자=수령자 펀딩에서 달성선 ≠ 목표인 데이터가 0건이다 — 차액이 구조적으로
  존재할 수 없다

- **SC-008**: 참여 확정 전 고지 2종이 모든 참여 경로에서 노출된다
- **SC-009**: 3계정(주최자·수령자·참여자)으로 개설 → 참여 2명 → 달성선 초과 마감 → 차액
  자동 결제, 그리고 미달 → 전액 환불의 두 시연 경로가 완주된다
- **SC-010**: 폭 360px에서 M4 화면 8종이 가로 스크롤 없이 동작한다

- **2단계 예약** (도메인 모델 §6 동시성) — 예약 시점 잔여 잠금, 만료는 지연 평가(§8)
- **지분 공개 3단계** (도메인 모델 §6 · PRD R5)
- **환불 상태를 펀딩에 두지 않는다** (도메인 모델 §6) — 미달/취소 구분을 지키기 위해
- **차액 결제 고지는 동의와 별개** (도메인 모델 §5 `funding_organizer_topup`)
