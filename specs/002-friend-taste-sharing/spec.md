# Feature Specification: 친구에게 취향이 전달된다 (마일스톤 2)

**Feature Branch**: `002-friend-taste-sharing`

**Created**: 2026-08-28

**Status**: Draft

**Input**: User description: "m2 시작하자."

---

## 이 기능이 무엇인가

M1에서 사용자는 자기 취향을 남겼다. 그런데 **그 취향을 볼 사람이 아직 없다.** M2는 그 통로를
만든다. 링크 하나를 보내면 받은 사람이 바로 친구가 되고, 서로의 취향을 볼 수 있게 된다.

M1이 이 제품의 자산(맞춤 취향 데이터)을 만들었다면, M2는 **그 자산이 처음으로 쓰이는 지점**이다.
여기까지 오면 제품의 이야기가 완결된다 — 취향을 적으면, 친구가 그것을 본다.

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 링크로 친구가 된다 (Priority: P1)

취향을 등록한 사용자가 친구 추가 링크를 발급받아 지인에게 보낸다. 링크를 받은 사람이 열면
발급자의 표시명과 대표 태그가 보이고, 가입하면 **승인 절차 없이 곧바로 친구가 된다.**
성사되면 발급자에게 알림이 간다.

**Why this priority**: 이것이 M2의 전부다. 친구 관계가 없으면 취향 열람도, 친구 목록도,
관계 해제도 존재할 수 없다. **이 스토리 하나만 되어도 마일스톤의 핵심 가정("링크 한 번이면
관계가 맺어진다")을 검증할 수 있다.**

**Independent Test**: 계정 두 개로, A가 링크를 발급해 B에게 전달하고 B가 그 링크로 가입하면
서로의 친구 목록에 상대가 나타나는 것까지 확인하면 된다. 취향 열람 화면 없이도 검증된다.

**Acceptance Scenarios**:

1. **Given** 온보딩을 마친 사용자 A, **When** A가 친구 추가 화면에 들어간다,
   **Then** 공유 가능한 링크와 만료 시점, **"받은 사람이 바로 친구가 됩니다"** 고지가 함께 보인다
2. **Given** A에게 이미 유효한 링크가 있다, **When** A가 친구 추가 화면에 다시 들어간다,
   **Then** 새 링크를 발급하지 않고 **기존 링크를 그대로** 보여준다
3. **Given** 비가입자 B가 A의 유효한 링크를 연다, **When** 화면이 뜬다,
   **Then** A의 표시명·프로필 이미지·대표 태그 2~3개만 보이고 **취향 항목과 취향 서술은 보이지 않는다**
4. **Given** B가 미리보기에서 시작하기를 누른다, **When** 가입과 온보딩을 마친다,
   **Then** A와 B가 친구가 되고 성사 화면이 뜬다
5. **Given** 이미 로그인한 C가 A의 유효한 링크를 연다, **When** C가 A와 아직 친구가 아니다,
   **Then** 미리보기를 건너뛰고 **즉시 친구가 성사된다**
6. **Given** 링크로 친구가 성사됐다, **When** 성사 직후,
   **Then** 발급자 A에게 **누가 링크로 친구가 되었는지 알림**이 전달된다
7. **Given** A가 자기 링크를 자기가 연다, **When** 화면이 뜬다,
   **Then** 본인 링크임을 알리고 **친구를 성사시키지 않는다**

### User Story 2 - 친구의 취향을 본다 (Priority: P1)

친구가 된 사용자가 상대의 취향 카드를 연다. `원하는 것`·`이미 있어요`·`관심 없어요`와
취향 서술이 전부 보인다. 항목별 공개 설정은 없다 — 친구면 전부 보이고, 친구가 아니면 아무것도
보이지 않는다.

**Why this priority**: **이것이 마일스톤 2의 완료 판정 화면이다.** US1이 관계를 만들었다면
US2가 그 관계의 값을 실현한다. 둘 다 P1인 이유는, US1만 있으면 "친구는 됐는데 볼 게 없는"
상태로 끝나기 때문이다.

**Independent Test**: 이미 친구인 두 계정으로, 한쪽이 상대의 취향 카드를 열어 M1에서 등록한
항목이 그대로 보이는지 확인한다. 링크 발급 흐름 없이 검증된다.

**Acceptance Scenarios**:

1. **Given** A와 B가 친구다, **When** B가 A의 취향 카드를 연다,
   **Then** A의 세 종류 취향 항목과 취향 서술이 **필터 없이 전부** 보인다
2. **Given** A가 온보딩만 하고 `원하는 것`과 취향 서술을 비워뒀다, **When** B가 A의 카드를 연다,
   **Then** 있는 것만 보이고 **화면이 성립한다** — 비어 있음을 탓하는 문구를 쓰지 않는다
3. **Given** B가 A와 친구가 아니다, **When** B가 A의 취향에 접근을 시도한다,
   **Then** 거부된다
4. **Given** B에게 친구가 여러 명 있다, **When** B가 친구 탭을 연다,
   **Then** 활성 친구만 목록에 나오고 각자의 **대표 태그**가 함께 보인다
5. **Given** B에게 친구가 한 명도 없다, **When** B가 친구 탭을 연다,
   **Then** 링크로 시작하라는 안내와 링크 발급 진입점이 보인다

---

### User Story 3 - 링크를 통제한다 (Priority: P2)

링크는 다회용이고 만료가 있다. 발급자는 자기 링크가 몇 명에게 쓰였는지 보고, 원하면 즉시
중지할 수 있다. 중지되거나 만료된 링크는 아무것도 노출하지 않는다.

**Why this priority**: 승인 단계를 없앤 대가다. **통제 수단이 만료·중지·알림 셋뿐이므로**
그중 둘이 여기 있다. 다만 링크를 뿌린 직후에는 문제가 드러나지 않아 US1·US2보다 뒤에 둔다.

**Independent Test**: 링크를 발급해 사용 횟수를 확인하고, 중지한 뒤 그 링크를 열면 아무것도
보이지 않는 것까지 확인한다.

**Acceptance Scenarios**:

1. **Given** A의 링크가 3명에게 쓰였다, **When** A가 링크 관리 화면을 연다,
   **Then** 사용 인원수와 만료까지 남은 기간이 보인다
2. **Given** A가 링크를 중지한다, **When** 누군가 그 링크를 연다,
   **Then** 만료 안내만 보이고 **A의 표시명조차 노출되지 않는다**
3. **Given** 링크가 만료됐다 · 중지됐다 · 존재하지 않는다, **When** 각각을 연다,
   **Then** **셋 다 같은 문구**가 나온다 — 어느 경우인지 구분해 알리지 않는다
4. **Given** A가 링크를 중지했다, **When** A가 친구 추가 화면에 들어간다,
   **Then** 새 링크를 발급받을 수 있다

---

### User Story 4 - 친구를 해제한다 (Priority: P3)

친구 관계를 끊는다. 끊으면 서로의 취향을 볼 수 없게 된다. 해제 전에 무엇이 닫히는지 알려준다.

**Why this priority**: 관계를 맺을 수 있으면 끊을 수도 있어야 하지만, **끊을 관계가 먼저
있어야 한다.** US1~US3 없이는 검증조차 불가능하다.

**Independent Test**: 친구인 두 계정에서 한쪽이 해제한 뒤, 양쪽 모두 상대의 취향에 접근할 수
없는 것을 확인한다.

**Acceptance Scenarios**:

1. **Given** A와 B가 친구다, **When** B가 해제를 시도한다,
   **Then** 무엇이 닫히는지 안내하고 확인을 받는다
2. **Given** B가 해제를 확인했다, **When** 해제된다,
   **Then** 양쪽 친구 목록에서 서로가 사라지고 **양방향으로** 취향 접근이 차단된다
3. **Given** A와 B가 해제된 이력이 있다, **When** 둘이 다시 링크로 친구가 된다,
   **Then** 정상적으로 성사되고 **과거 해제 이력이 재추가를 막지 않는다**
4. **Given** A와 B가 해제됐다, **When** A가 B의 취향 카드 주소로 직접 접근한다,
   **Then** 거부된다

---

### Edge Cases

- **이미 친구인 사람이 링크를 연다** → 미리보기나 성사 화면 대신 그 친구의 취향 카드로 바로 간다
- **가입·온보딩 도중에 링크가 만료된다** → 가입은 완료시키고 친구 성사만 하지 않는다.
  "링크가 만료돼 친구 추가는 못 했어요. 가입은 완료됐습니다."
- **두 사람이 서로의 링크를 동시에 연다** → 관계는 **한 쌍당 하나만** 성립한다. 중복 생성되지 않는다
- **같은 링크를 여러 명이 동시에 연다** → 다회용이므로 전부 성사된다. 사용 횟수가 정확히 누적된다
- **상대가 취향을 하나도 등록하지 않았다** → 친구 목록의 대표 태그 자리를 **비워둔다.**
  "아직 등록한 취향이 없어요" 같은 문구를 쓰지 않는다 — 상대의 미입력을 노출하는 꼴이 된다
- **온보딩을 마치지 않은 사용자가 링크를 발급하려 한다** → 발급 자체는 막지 않되,
  취향이 비어 있으면 미리보기에 대표 태그가 뜨지 않는다
- **해제 직후 상대가 이미 열어둔 취향 카드를 새로고침한다** → 접근이 차단된다.
  이미 렌더된 화면을 신뢰하지 않는다

## Requirements *(mandatory)*

### Functional Requirements

#### 친구 초대 링크

- **FR-001**: 시스템은 사용자마다 **추측할 수 없는** 친구 초대 링크를 발급해야 한다
- **FR-002**: 링크는 **다회용**이어야 한다 — 여러 명이 같은 링크로 친구가 될 수 있다
- **FR-003**: 링크에는 **만료 시점**이 있어야 하며, 사용자에게 만료까지 남은 기간을 보여야 한다
- **FR-004**: 사용자에게 유효한 링크가 이미 있으면 시스템은 **새 링크를 발급하지 않고 기존 링크를 반환**해야 한다
- **FR-005**: 사용자는 자기 링크를 **즉시 중지**할 수 있어야 하며, 중지된 링크는 그 시점부터 무효해야 한다
- **FR-006**: 사용자는 자기 링크가 **몇 명에게 사용되었는지** 볼 수 있어야 한다
- **FR-007**: 시스템은 링크가 **만료·중지·부재**인 세 경우를 **구분할 수 없는 하나의 응답**으로 처리해야 한다
  (토큰 탐색에 힌트를 주지 않기 위함)

#### 미리보기 (비가입 열람)

- **FR-008**: 유효한 링크를 연 사람은 **로그인 없이** 발급자의 표시명·프로필 이미지·대표 태그 2~3개를 볼 수 있어야 한다
- **FR-009**: 미리보기는 발급자의 **취향 항목과 취향 서술을 노출하지 않아야 한다**
- **FR-010**: 미리보기는 **가려진 항목의 이름**(원하는 것 / 이미 있는 것 · 관심 없는 것 / 취향 서술)을
  보여야 한다 — 값은 보이지 않되 무엇이 있는지는 알린다
- **FR-011**: 유효하지 않은 링크의 미리보기는 **발급자의 표시명조차 노출하지 않아야 한다**
- **FR-012**: 대표 태그는 사용자가 고르지 않고 **`원하는 것` 항목에서 자동으로 뽑아야 한다**

#### 친구 관계

- **FR-013**: 유효한 링크로 접근한 사람은 **승인 절차 없이 즉시 친구**가 되어야 한다
- **FR-014**: 시스템은 링크 발급 시점에 **"받은 사람이 바로 친구가 됩니다"를 발급자에게 고지**해야 한다
- **FR-015**: 한 쌍의 사용자 사이에 **활성 친구 관계는 최대 하나만** 존재해야 한다 (요청 방향과 무관하게)
- **FR-016**: 시스템은 **자기 자신과 친구가 되는 것을 막아야 한다**
- **FR-017**: 친구가 성사되면 시스템은 **발급자에게 누가 친구가 되었는지 알려야 한다**
- **FR-018**: 사용자는 **활성 친구 목록**을 각자의 대표 태그와 함께 볼 수 있어야 한다
- **FR-019**: 가입·온보딩 도중 링크가 무효해지면 시스템은 **가입은 완료시키고 친구 성사만 취소**해야 한다

#### 취향 열람 · 접근 제어

- **FR-020**: 활성 친구인 사용자는 상대의 **취향 항목 전체와 취향 서술**을 볼 수 있어야 한다
- **FR-021**: 시스템은 **항목별 공개 범위를 두지 않아야 한다** — 친구면 전부, 아니면 전무
- **FR-022**: 활성 친구가 아닌 사용자의 취향 접근은 **거부**되어야 한다
- **FR-023**: 취향이 비어 있는 친구의 카드도 **오류 없이 렌더**되어야 한다

#### 친구 해제

- **FR-024**: 사용자는 친구 관계를 해제할 수 있어야 하며, 해제 전 **무엇이 닫히는지 고지**받아야 한다
- **FR-025**: 해제는 **양방향**으로 즉시 적용되어야 한다
- **FR-026**: 해제된 관계는 **이력으로 남아야 하며**, 그 이력이 **재친구 추가를 막지 않아야 한다**
- **FR-027**: 시스템은 관계를 **어느 쪽이 언제 끊었는지** 기록해야 한다

---

### Key Entities *(include if feature involves data)*

- **Friendship (친구 관계)**: 두 사용자 사이의 관계. **한 쌍당 한 개의 기록**으로 표현하며 양쪽에
  복제하지 않는다. 누가 먼저 요청했는지, 어느 링크로 맺어졌는지, 활성인지 해제됐는지,
  해제됐다면 언제 누가 끊었는지를 담는다. 해제해도 기록은 지우지 않는다 — 이력과 재추가 판정에 쓴다
- **FriendInviteLink (친구 초대 링크)**: 발급자, 추측 불가능한 식별자, 만료 시점, 중지 여부,
  사용 횟수를 담는다. 다회용이다
- **User (사용자)** — *M1에서 존재*: 표시명과 프로필 이미지가 미리보기에 노출된다
- **TasteProfile · TasteItem (취향)** — *M1에서 존재*: 친구 열람의 대상.
  M2는 **이 데이터를 읽기만 하고 구조를 바꾸지 않는다**

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 링크를 받은 사람이 **처음 열어본 시점부터 3분 안에** 친구가 되어 상대 취향을 볼 수 있다
- **SC-002**: 링크 발급자가 **화면 하나 안에서** 링크 확인·복사·공유를 끝낸다 — 추가 이동이 없다
- **SC-003**: 링크를 발급한 사용자 5명 중 **4명 이상이** "받은 사람이 승인 없이 바로 친구가 된다"는
  사실을 링크를 보내기 전에 알고 있다고 답한다
- **SC-004**: 친구가 아닌 사용자의 취향 열람 시도가 **100% 차단된다** — 목록·상세·직접 주소 접근 전부
- **SC-005**: 만료·중지·부재 링크 세 경우의 응답이 **외부에서 구분되지 않는다**
- **SC-006**: 폭 360px에서 M2의 모든 화면이 **가로 스크롤 없이** 동작한다
- **SC-007**: 취향을 하나도 등록하지 않은 친구의 카드에서도 **오류 없이 화면이 성립한다**
- **SC-008**: 같은 링크를 **동시에 여러 명이 사용해도** 사용 횟수가 정확히 누적되고
  관계가 중복 생성되지 않는다

## Assumptions

### 확정된 것을 그대로 따른 것

- **승인 절차를 두지 않는다.** 도메인 모델 3-3의 결정이며, 대가로 만료·중지·발급자 알림 셋을 둔다.
  이 스펙은 그 결정을 재검토하지 않는다
- **항목별 공개 설정을 두지 않는다** (도메인 모델 D2). 친구면 전부 공개다.
  친구 그룹별 공개는 Future로 연기돼 있다
- **해제는 기록을 지우지 않는다** (도메인 모델 D3). 재추가 시 기존 기록을 되살리지 않고 새로 만든다
- **대표 태그는 `원하는 것`에서 최신순으로 뽑는다.** 도메인 모델 §13-5에 "최신순 3건으로 충분한가"가
  열린 항목으로 남아 있으나, **화면 명세가 최신순을 전제하므로 그대로 간다.**
  M2 착수 시점에 닫기로 한 항목이니 구현 전에 확정한다
- **링크 만료 기간은 7일**로 둔다 (화면 명세 SCR-M2-02)

### 범위 밖으로 밀어낸 것

- **다가오는 일정 (`Event`)**: 화면 명세 SCR-M2-01·06이 "생일 D-3" 같은 일정을 보여주지만,
  `Event`는 **M3 엔티티다** (도메인 모델 §11). M2에서는 **일정 영역을 만들지 않는다.**
  화면 명세가 M2 화면에 M3 데이터를 얹어 둔 것으로, 이 스펙은 M2 경계를 따른다
- **`이 취향에 맞는 선물 보기`**: 상품이 없으므로 M2에서는 **버튼을 숨긴다** (화면 명세도 그렇게 지시)
- **진행 중 거래가 있을 때의 해제 예외 (D3)**: 거래(`GiftRequest`·`Funding`)가 M3·M4 엔티티라
  M2에는 진행 중 거래가 존재할 수 없다. **해제 시 전면 차단만 구현한다.**
  다만 해제 확인 문구의 "진행 중인 선물·펀딩은 그대로 진행됩니다"는 M3에서 참이 되므로,
  M2에서는 **그 문장을 넣지 않는다**
- **알림 목록 화면**: `Notification`도 M3 엔티티다. FR-017의 알림은 **발급자가 확인할 수 있는 형태로
  전달**되기만 하면 되고, 알림 센터 화면은 M3에서 만든다

### 그 밖의 가정

- M1이 완료된 상태를 전제한다 — 사용자·취향 프로필·취향 항목이 이미 존재한다
- 링크 공유는 운영체제의 공유 기능에 맡긴다. 앱 안에 자체 메시지 발송을 만들지 않는다
- 미리보기는 로그인이 필요 없으므로 **앱 셸(하단 탭) 밖의 화면**이다
