# Quickstart: 친구에게 취향이 전달된다 (마일스톤 2)

**Date**: 2026-08-28 | **Plan**: [plan.md](./plan.md)

이 기능이 실제로 동작하는지 확인하는 절차다. 구현 방법이 아니라 **검증 방법**을 담는다.
스키마는 [data-model.md](./data-model.md), 인터페이스는
[contracts/server-actions.md](./contracts/server-actions.md)를 본다.

## 전제 조건

M1이 완료된 상태에서 시작한다. 추가로 필요한 것:

| 항목 | 값 |
|---|---|
| **테스트 계정 2개** | M2의 모든 시나리오가 "A가 링크를 만들고 B가 받는" 두 주체 구조다 (R10) |
| 개발 서버 포트 | **3000 고정** — `playwright.config.ts`의 `baseURL`·`webServer`가 3000이다 |

`.env.local`에 두 줄을 더한다.

```
E2E_USER2_EMAIL=
E2E_USER2_PASSWORD=
```

> Supabase → Authentication → Users → Add user → **Auto Confirm User 체크**.
> 실제 메일함이 없어도 된다.
>
> ⚠️ **비어 있으면 두 계정이 필요한 E2E가 실패가 아니라 skip 된다.** 초록으로 보이지만
> 한 줄도 안 돈다. M1에서 이 skip이 픽스처 버그를 오래 가렸다 —
> 실행 결과에서 **`skipped` 수를 반드시 확인한다.**

## 준비

```bash
npm install
npx prisma migrate dev          # C3 partial unique index · C4 CHECK 포함
npm run dev                     # 반드시 3000
```

`npx prisma db seed`는 다시 돌릴 필요 없다 — M2는 `Category`를 건드리지 않는다.

> **새 환경은 반드시 `migrate deploy`(또는 `migrate dev`)로 만든다.** `db push`는
> raw SQL 마이그레이션의 partial index와 CHECK를 만들지 않는다 — M1의 `NULLS NOT DISTINCT`와
> 같은 함정이다.

## 검증 시나리오

각 시나리오는 [spec.md](./spec.md)의 수용 시나리오에 대응한다.

### V1 — 링크로 친구가 된다 (US1)

1. A로 로그인 → 친구 탭 → `+` → 링크 발급 화면.
   **"받은 사람이 바로 친구가 됩니다"가 보이는지** 확인 (FR-014)
2. 같은 화면에 다시 들어간다 → **새 링크가 발급되지 않고 같은 링크**가 보인다 (FR-004)
3. 링크를 복사해 **로그아웃 상태의 다른 브라우저**에서 연다 →
   A의 표시명·이미지·대표 태그만 보이고 **취향 항목과 서술은 보이지 않는다** (FR-009)
4. "가려진 것" 목록(원하는 것 / 이미 있는 것·관심 없는 것 / 취향 서술)의 **이름이 보이는지**
   확인 (FR-010)
5. B로 가입·온보딩 완료 → **성사 화면**이 뜨고 양쪽 친구 목록에 서로가 나타난다
6. A의 **알림 목록**에 "B가 링크로 친구가 되었습니다"가 미읽음으로 있다 (FR-017)
7. A가 자기 링크를 자기가 연다 → **"본인 링크입니다"**, 친구 성사되지 않는다 (FR-016)

### V2 — 친구의 취향을 본다 (US2)

1. B가 A의 취향 카드를 연다 → 세 종류 항목과 취향 서술이 **전부** 보인다 (FR-020·FR-021)
2. 친구 목록에서 **대표 태그가 `원하는 것` 최근 3건**인지 확인. `원하는 것`을 하나 더 등록하면
   태그가 바뀐다 (FR-012)
3. `원하는 것`을 0건으로 만든다 → 친구 목록의 **태그 자리가 빈다.**
   "아직 없어요" 같은 문구가 뜨지 않는다
4. 취향을 하나도 등록하지 않은 계정의 카드를 연다 → **오류 없이 화면이 성립한다** (FR-023·SC-007)
5. 친구가 아닌 사용자의 `/friends/{userId}`에 **직접 주소로** 접근 → 거부된다 (FR-022)

### V3 — 링크를 통제한다 (US3)

1. 링크 관리 화면 → **사용 인원수와 만료까지 남은 기간**이 보인다 (FR-006)
2. 링크를 중지 → 그 링크를 열면 **A의 표시명조차 안 보인다** (FR-011)
3. **만료 · 중지 · 없는 토큰** 셋을 각각 연다 → **같은 문구**가 나온다 (FR-007·SC-005)
   > 만료는 DB에서 `expiresAt`을 과거로 바꿔 만든다
4. 중지 후 친구 추가 화면 → **새 링크를 발급받을 수 있다**
5. 알림을 눌러 **그 친구의 취향 카드로 이동**하는지, 해당 알림이 읽음으로 바뀌는지 (FR-032)
6. **모두 읽음** → 전부 읽음으로 바뀐다. 이미 읽었던 알림의 읽은 시각은 **바뀌지 않는다** (FR-031)
7. 알림 0건 → **빈 상태 안내**가 보인다 (FR-034)

### V4 — 친구를 해제한다 (US4)

1. 친구 상세 → `⋮` → 해제 → **무엇이 닫히는지 안내**가 보인다 (FR-024)
   > "진행 중인 선물·펀딩은 그대로 진행됩니다" 문구는 **없어야 한다** — M2에는 거래가 없다
2. 해제 확인 → **양쪽** 친구 목록에서 사라지고 양방향으로 접근이 차단된다 (FR-025)
3. 해제된 상대의 취향 카드에 **직접 주소로** 접근 → 거부된다
4. **과거 성사 알림이 남아 있는지** 확인. 눌러도 취향 카드 접근은 거부된다
5. 같은 상대와 **다시 링크로 친구가 된다** → 정상 성사된다 (FR-026)

### V5 — 제약 (Edge Cases)

1. **DB 제약이 실제로 걸렸는지** 확인한다. C3·C4가 없으면 화면상 완전히 정상으로 보이고,
   중복 관계가 쌓인 뒤에야 드러난다.

   ```sql
   -- C3: 같은 쌍의 활성 관계를 두 번 넣으면 거부되어야 한다 (순서를 바꿔도)
   SELECT indexname FROM pg_indexes WHERE indexname = 'friendship_pair_active';
   -- C4: 자기 자신과의 관계가 거부되어야 한다
   SELECT conname FROM pg_constraint WHERE conname = 'friendship_not_self';
   ```

   > 두 행이 조회되지 않으면 **마이그레이션이 안 걸린 것이다.** `db push`로 만든 DB가 흔한 원인이다.

2. **같은 링크를 여러 명이 동시에** 사용 → 전부 성사되고 `usedCount`가 정확히 누적된다 (SC-008)
3. **이미 친구인 사람이 링크를 다시** 연다 → 친구 상세로 직행하고 **`usedCount`가 오르지 않는다** (R5)
4. 가입·온보딩 도중 링크가 만료된다 → **가입은 완료되고 친구 성사만 취소**된다 (FR-019)
   > 링크를 연 뒤 온보딩 중에 DB에서 `revokedAt`을 채워 만든다

### V6 — 반응형 (SC-006)

폭 **360px**에서 V1~V4를 다시 밟는다. 가로 스크롤이 생기면 실패다. **알림 목록을 포함한다.**

```bash
npm run test                              # Vitest — 단위·통합

```
