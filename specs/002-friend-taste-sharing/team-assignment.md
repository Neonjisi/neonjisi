## 1. M1과 무엇이 달라지나

### 자르는 방향을 바꿨다

M1은 **층으로** 잘랐다 — J는 DB·서버, D는 인증·DAL·테스트, H는 화면 전부. 화면과 서버 로직의
양이 비슷해서 잘 통했다.

M2는 **스토리로** 자른다. 각 스토리가 화면과 서버 로직을 둘 다 갖고 있어 저절로 균형이 맞는다.

```
Phase 1  준비        전원 (각자 자기 컴퓨터)
Phase 2  기반 공사    J D H       ← 여기가 흔들리면 전부 다시 만짐
Phase 3  US1 (MVP)   J H D       ← 링크로 친구가 된다
Phase 4  US2         H 중심      ← 마일스톤 완료 판정
Phase 5  US3         D 단독      ← 링크 통제 + 알림
Phase 6  US4         J 단독      ← 해제
Phase 7  마무리       전원
```

### 가장 큰 충돌원이 사라졌다

M1에서는 `app/taste/actions.ts` **한 파일**을 US3·US4가 함께 건드려서 "J가 혼자 소유한다"는
규칙으로 막았다. 규칙이 있어야 했던 건 파일이 하나였기 때문이다.

M2는 **Server Action을 파일 4개로 나눈다.** Next.js는 Action을 한 파일에 모으라고 요구하지 않는다.

```
app/friends/actions/
├── shared.ts          ← 기반 단계에서 D 가 먼저. 그 뒤로 아무도 안 고침
├── accept-invite.ts   ← US1 · J
├── invite-link.ts     ← US3 · D
├── notification.ts    ← US3 · D
└── friendship.ts      ← US4 · J
```

**나누면 소유 규칙 자체가 필요 없어진다.** US1·US3·US4가 서로 만나지 않는다.

## 3. 공통 — 전원이 각자 하는 것

### T001 · T002 — 두 번째 E2E 테스트 계정

**M2에서 새로 생긴 것이다.** M2의 모든 시나리오가 "A가 링크를 만들고 B가 받는" **두 주체
구조**라 계정이 하나로는 검증이 안 된다. 자기 자신과는 친구가 될 수 없다(FR-016).

```bash
# .env.local 맨 아래
E2E_USER2_EMAIL=
E2E_USER2_PASSWORD=
```

> Supabase → Authentication → Users → Add user → **Auto Confirm User 체크**.
> 실제 메일함이 없어도 된다. 주소는 지어내면 된다.
>
> 🔒 `.env.local`은 절대 커밋하지 않는다.

### ⚠️ 비어 있으면 실패가 아니라 skip 된다

**M1에서 이 함정에 걸렸다.** 환경 변수가 비면 인증 E2E가 **조용히 건너뛰어진다.** 초록으로
보이지만 한 줄도 안 돈다. 그 skip이 픽스처 버그를 몇 시간 가렸고, 계정을 만들고 나서야
5건이 깨져 있던 것이 드러났다.

**`npm run test:e2e` 결과에서 `passed` 숫자만 보지 말고 `skipped`가 있는지 본다.**

### 개발 서버는 `:3000` 고정

`playwright.config.ts`의 `baseURL`과 `webServer`가 3000이다. 다른 포트로 띄우면 E2E가 안 돈다.

> **다른 Supabase 프로젝트를 같이 띄우지 않는다.** `localhost` 쿠키는 포트를 가리지 않아서
> `sb-*` 쿠키가 함께 쌓이고, 헤더 상한(16KB)을 넘으면 **HTTP 431**로 페이지가 아예 안 뜬다.
> 그럴 땐 브라우저에서 `localhost` 쿠키를 지운다.

> 재추가를 막지 않는다. Prisma 문법으로 표현되지 않아 raw SQL로 넣는다.

> **M1의 T010(`NULLS NOT DISTINCT`)과 같은 함정이다.** 그때 T011이 없었으면 제약이 걸렸는지
> 알 수 없었다. **T005가 이번의 T011이다.**

## 5. 왜 이렇게 나눴나 — 충돌 지도

**Server Action 파일을 나눠서 M1의 가장 큰 충돌원이 사라졌다.** 남은 것은 셋이다.

| 파일 | 건드리는 스토리 | 해법 |
|---|---|---|
| `lib/dal/invite.ts` | 기반(T014) · US1(T020·T021) · US3(T041) | **J가 소유한다.** T041은 US3 태스크지만 J가 쓴다 |
| `app/friends/[userId]/page.tsx` | US2(T037) · US4(T053) | H가 US2를 먼저 끝내고 J가 진입점을 얹는다 |
| `app/friends/page.tsx` | US1(T028) · US2(T035 경유) | H가 둘 다 쥐고 있어 충돌이 아니다 |
| `lib/dal/friend.ts` | US1(T022) · US2(T032~T034) | H가 둘 다 쥐고 있어 충돌이 아니다 |

**결과적으로 실제 조율이 필요한 것은 두 줄뿐이다** — `lib/dal/invite.ts`(J 소유)와
`app/friends/[userId]/page.tsx`(H → J 순서).

## 6. 협업 규칙

M1에서 쓰던 것을 그대로 잇는다. **M2에서 새로 생긴 것만 굵게** 표시했다.

| 규칙 | 이유 |
|---|---|
| **`lib/dal/`을 반드시 거친다** | M1과 같다. DB 레벨 2차 방어선이 없어 DAL이 유일한 접근 제어 지점이다 |
| **테스트를 먼저 쓴다** | 각 스토리의 테스트 태스크가 구현보다 앞 번호다 |
| **마이그레이션은 J만 만든다** | 여러 명이 만들면 팀 전원의 DB가 어긋난다 |
| **`.env.local`은 커밋하지 않는다** | |
| **브랜치를 따서 작업하고 push, 각자 pull** | PR 없이 간다 |
| **개발 서버는 `:3000`** | Playwright `baseURL` 고정 |
| **`skipped` 수를 확인한다** | 계정이 없으면 실패가 아니라 skip 된다 |
| **착수 전에 한 줄 공유한다** | M1에서 두 사람이 같은 E2E 픽스처 버그를 동시에 고쳤다 |

### Next.js 16 주의 (M1과 동일)

- **`middleware.ts`가 아니라 `proxy.ts`다**
- **비동기 서버 컴포넌트는 단위 테스트가 어렵다.** 화면 검증은 Playwright로 한다
