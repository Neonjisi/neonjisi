# Feature Specification: 선물이 수령자 확인을 거쳐 결정된다 (마일스톤 3)

**Feature Branch**: `003-gift-request-payment`

**Created**: 2026-08-31

**Status**: Planned — [plan.md](./plan.md) 작성 완료 (2026-08-31)

**Input**: User description: "M3 — 선물이 수령자 확인을 거쳐 결정된다. 주는 사람이 카탈로그에서 상품을 골라 선물 요청을 보내면, 수령자가 제한 시간 안에 승인하거나 최초 요청 금액 이하의 대안 상품을 제시한다. 어느 경로든 확정 시 등록된 결제수단으로 자동 결제가 실행되고, 실패 시 재시도로 복구된다."

---

## 이 기능이 무엇인가

M1이 이 제품의 자산(맞춤 취향 데이터)을 만들었고, M2가 그것을 친구에게 전달했다. M3는
**그 취향이 실제 거래로 이어지는 층**이다 — 주는 사람이 카탈로그에서 고르고, 수령자가
확인하고, 자동으로 결제된다.

두 가지가 이 마일스톤의 정체성이다.

1. **어긋난 선물이 걸러진다.** 수령자가 `관심 없어요`로 표시한 카테고리는 목록에서 빠지고,
   상세에서 막히고, 요청 생성에서 다시 거부된다. "짐작으로 고르면 어긋난다"는 Problem이
   화면에 드러나는 지점이다.
2. **거절이 없다.** 수령자의 선택지는 승인 / 대안 제시 / 무응답(→ 만료) 셋뿐이다.
   거절 상태를 만들지 않는 것 자체가 "거절이 아닌 대안 제시로 읽혀야 한다"는 요구사항의
   구현이다.

돈이 오가는 첫 마일스톤이다. 자동 결제는 사전 동의로 위임받은 권한이며, 그 동의는
구체적이어야 하고(금액을 숫자로, 별도 화면에서), 문구의 모든 버전이 복원 가능해야 한다.

  → A: **혼합** — 시뮬레이션 기본, 같은 인터페이스 뒤에 실연동을 숨기고 환경 변수로 전환.
  **E2E는 항상 시뮬레이션으로 돈다** — 테스트가 실결제를 만드는 경로를 봉쇄한다.
  "언제 실키를 붙이나"는 결제 실행 단계(US5) 착수 시점으로 미룬다
- Q: 일정은 홈의 목록형 표시로 충분한가, 별도 월간 캘린더 뷰가 필요한가? (P0-2)
  → A: **목록형으로 충분** — 화면 명세 설계 그대로. 월간 뷰를 만들지 않는다
- Q: 대안 제시 진입 버튼 문구로 화면 명세 제안 "다른 것도 좋아요"를 채택하나? (P0-3)
  → A: **채택** — 확정 문구다. 수신 화면·재선택·알림 문구 세트가 이 톤(거절 아님, 사실 서술)을 따른다
- Q: 재결제 동의 화면 v1 문구로 SCR-M3-09 초안을 확정하나? (P0-4)
  → A: **확정** — "OO님이 다른 상품을 고를 수 있습니다. 그 경우 [N]원 이하의 상품으로
  결제됩니다. 차액은 청구하지도, 돌려드리지도 않습니다. 결제 결과는 알려드립니다."
  금액은 요청마다 숫자로 삽입되는 템플릿이며, 이 문구가 `consent_version` v1이다.
  이후 수정마다 버전을 올린다

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 상품을 탐색하면 어긋난 선물이 걸러진다 (Priority: P1)

주는 사람이 선물 탭에서 상품을 검색·탐색한다. 받을 친구를 고르면 그 친구가 `관심 없어요`로
표시한 카테고리의 상품이 목록에서 빠지고, 상세 화면에서는 취향 매칭 여부가 배너로 보이며,
`관심 없어요` 상품은 선물하기 자체가 막힌다. 친구 맞춤 추천은 `원하는 것` 매칭을 우선으로
보여주고 **무엇을 걸러냈는지 밝힌다.**

**Why this priority**: 이것이 이 제품의 핵심 가치("잘못된 선물 걸러내기")가 처음으로 화면에
드러나는 지점이다. 카탈로그 없이는 어떤 요청도 만들 수 없다.

**Independent Test**: 취향을 등록한 친구 계정 하나만 있으면, 요청·결제 없이 목록 필터링과
상세 차단만으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 친구 민수가 카테고리 X를 `관심 없어요`로 표시했다, **When** 내가 선물 탭에서
   대상 필터로 민수를 고른다, **Then** 카테고리 X의 상품이 목록에서 빠진다
2. **Given** 민수가 대상 필터로 선택된 상태, **When** 검색으로 카테고리 X의 상품 상세에
   진입한다, **Then** 선물하기가 비활성이고 "민수님이 관심 없다고 한 종류예요"가 보인다 —
   **목록 필터를 우회해도 막힌다**
3. **Given** 민수의 `원하는 것`과 카테고리·상세가 일치하는 상품, **When** 상세를 연다,
   **Then** 긍정 배너("원하는 것에 적어둔 항목입니다")가 보인다
4. **Given** 민수의 `이미 있어요`와 카테고리가 일치하는 상품, **When** 상세를 연다,
   **Then** 주의 배너가 보이되 **선물하기는 가능하다** — "이미 있어요"와 "관심 없어요"는 다르다
5. **Given** 민수와 활성 친구다, **When** 친구 맞춤 추천을 연다, **Then** `원하는 것` 매칭
   섹션 · 같은 카테고리 확장 섹션 · **제외 안내**("텀블러·지갑은 빼고 보여드리고 있어요")가 보인다
6. **Given** 민수가 `원하는 것`을 하나도 안 적었다, **When** 추천을 연다, **Then** 그 사실을
   알리고 `관심 없어요` 제외 전체 카탈로그를 보여준다
7. **Given** 대상 필터 결과가 0건이다, **When** 목록이 뜬다, **Then** 전체에서 고르라는
   안내가 보인다 — 빈 목록만 두지 않는다
8. **Given** 민수와 친구가 아니다, **When** 민수 맞춤 추천에 접근한다, **Then** 거부된다

### User Story 2 - 결제수단을 등록한다 (Priority: P1)

주는 사람이 카드를 등록한다. 카드 정보는 결제대행사가 보관하고 이 서비스는 재결제에 필요한
키만 보관한다. **등록은 한 번, 동의는 요청마다** — 등록된 수단은 이후 모든 요청에서 재사용된다.

**Why this priority**: 결제수단이 요청보다 앞선다. 이것 없이는 US3 이후가 전부 막힌다.

**Independent Test**: 요청 플로우 없이 등록 → 관리 화면 표시 → 삭제만으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 등록된 결제수단이 없다, **When** 카드 등록을 마친다, **Then** 활성 결제수단이
   생기고 "카드 정보는 넌지시에 저장되지 않습니다"가 화면에 보인다
2. **Given** 결제수단이 등록돼 있다, **When** 관리 화면을 연다, **Then** 카드 브랜드와
   마지막 4자리만 보인다 — 카드번호 원본은 어디에도 없다
3. **Given** 진행 중인 선물 요청이 참조하는 수단이다, **When** 삭제를 시도한다,
   **Then** "진행 중인 선물 요청 N건이 이 카드를 사용합니다" 경고 후 삭제는 허용되며,
   결제 실패 경로로 이어질 수 있음을 고지한다
4. **Given** 수단이 만료 상태다, **When** 관리 화면을 연다, **Then** 재등록 유도가 보이고
   마이 탭에 배지가 켜진다
5. **Given** 요청 플로우 도중 결제수단이 없다, **When** 등록 화면으로 강제 진입해 등록을
   마친다, **Then** 원래 요청 플로우로 복귀한다

### User Story 3 - 선물 요청을 보낸다 (Priority: P1)

주는 사람이 상품을 확정하고, **별도 동의 화면**에서 "수령자가 요청 금액 이하의 다른 상품을
고를 수 있고 그 경우 자동 결제된다"에 동의한 뒤 요청을 보낸다. 수령자에게 알림이 가고
응답 기한 카운트다운이 시작된다.

**Why this priority**: 여기서 만든 요청이 US4·US5의 입력이다. 동의 기록은 자동 결제 권한
위임의 증빙이라 이 스토리의 정확성이 법·신뢰 양쪽에 걸려 있다.

**Independent Test**: 계정 2개로 요청 생성 → 수령자 홈·알림에 도착 확인 → 취소까지.
응답·결제 없이 검증된다.

**Acceptance Scenarios**:

1. **Given** 활성 친구 · 활성 결제수단 · 허용된 상품, **When** 요청 확인 → 동의 화면에서
   체크 → 전송한다, **Then** 응답 대기 요청이 생기고 수령자에게 알림이 가고 카운트다운이
   보인다
2. **Given** 동의 화면이다, **When** 체크하지 않았다, **Then** 전송 버튼이 비활성이다 —
   동의 없이 생성된 요청은 존재할 수 없다
3. **Given** 동의 문구가 보인다, **Then** 요청 금액 상한이 **숫자로** 박혀 있고, 차액을
   청구하지도 돌려주지도 않는다는 것과 결제 결과를 알려준다는 것이 함께 적혀 있다
4. **Given** 결제수단이 없다, **When** 요청을 시작한다, **Then** 등록 화면으로 강제 진입한다 (US2-5)
5. **Given** 상대와 친구가 아니거나 해제됐다, **When** 요청을 시도한다, **Then** 거부된다
6. **Given** 상대의 `관심 없어요` 카테고리 상품이다, **When** 화면 차단을 우회해 생성을
   시도한다, **Then** 생성 단계에서 다시 거부된다 — **3중 차단의 마지막 지점**
7. **Given** 요청이 응답 대기 상태다, **When** 주는 사람이 취소한다, **Then** 요청이 취소되고
   수령자는 더 이상 응답할 수 없다
8. **Given** 응답 대기가 아닌 상태다(결제 중 이후), **When** 취소를 시도한다, **Then** 불가하다

### User Story 4 - 수령자가 확인하고 결정한다 (Priority: P1)

수령자가 도착한 요청을 열면 **승인과 대안 제시 두 버튼만** 있다 — 거절 버튼은 없다.
승인하면 배송지를 입력하고, 대안 제시를 고르면 **요청 금액 이하**에서 다른 상품을 고른다.
어느 쪽이든 확정 즉시 자동 결제가 시작된다.

**Why this priority**: 이 마일스톤에서 정확성이 걸린 최대 위험 구간이다. 같은 요청이 두 번
결제되면 화면상 완전히 정상으로 보이면서 돈이 두 번 나간다.

**Independent Test**: 계정 2개로 승인 경로와 대안 경로를 각각 밟아 확정까지 확인한다.
결제 자체의 성공·실패는 US5에서 검증한다.

**Acceptance Scenarios**:

1. **Given** 요청이 도착했다, **When** 수신 화면을 연다, **Then** 승인 · 대안 제시 버튼과
   남은 시간, "요청 금액 이하에서 직접 고를 수 있어요" 안내가 보이고 **거절 버튼은 없다**
2. **Given** 수령자가 승인을 눌렀다, **When** 배송지를 입력하고 완료한다, **Then** 추가 조작
   없이 자동 결제가 시작된다
3. **Given** 대안 제시를 골랐다, **When** 재선택 화면이 뜬다, **Then** 요청 금액 이하 상품만
   보이고 **내 `원하는 것` 매칭이 우선** 노출된다
4. **Given** 대안을 골랐다, **When** 확정 직전 확인이 뜬다, **Then** "주는 사람에게 다른
   상품을 골랐다고 알려집니다"와 차액 미청구가 **확정 전에** 고지된다
5. **Given** 요청 금액을 넘는 상품이다, **When** 어떤 경로로든 대안으로 저장을 시도한다,
   **Then** 저장이 거부된다 — 화면 필터와 저장 계층 양쪽에서
6. **Given** 응답 기한이 지났다, **When** 수신 화면에 진입한다, **Then** 만료 안내만 보이고
   응답 버튼이 없다 — 진입 시점에 만료가 확정된다
7. **Given** 화면을 열어둔 채 기한이 지났다, **When** 승인·대안 확정을 누른다, **Then** 액션이
   실패하고 만료 안내로 전환된다
8. **Given** 주는 사람이 먼저 취소했다, **When** 수령자가 응답을 시도한다, **Then** "요청이
   취소되었어요"가 보인다
9. **Given** 같은 요청이다, **When** 동시에 두 번 승인이 들어온다(더블탭·중복 요청),
   **Then** 결제는 **정확히 1회**만 시도된다
10. **Given** 배송지 입력 화면이다, **Then** "이 주소는 이 선물에만 사용됩니다"가 보인다 —
    프로필 기본 배송지가 아니라 이 거래에만 제공되는 값이다
11. **Given** 대안이 확정됐다, **When** 주는 사람이 요청 상세를 연다, **Then** 원래 상품 →
    최종 상품 대조와 "차액 N원은 청구되지 않았습니다"가 보이고, 대안 제시 사실이 알림으로도
    전달돼 있다

### User Story 5 - 자동 결제가 실행되고 실패에서 복구된다 (Priority: P1)

확정 즉시 등록된 결제수단으로 자동 결제된다. 성공하면 양쪽에 알리고, 실패하면 주는 사람만
알고 재시도한다(결제수단 변경 포함). 재시도 상한을 넘기면 취소되고 **이때는 수령자에게도
반드시 알린다.**

**Why this priority**: 마일스톤 완료 판정이 여기다 — "승인·대안 제시 양쪽 경로로 자동 결제가
완료된다. 결제 실패 후 재시도로 복구된다."

**Independent Test**: 결제 성공·실패를 각각 만들 수 있는 환경에서, 성공 경로의 완료 화면과
실패 → 재시도 → 성공, 실패 → 상한 초과 → 취소 + 양쪽 고지를 확인한다.

**Acceptance Scenarios**:

1. **Given** 승인 또는 대안이 확정됐다, **When** 자동 결제가 성공한다, **Then** 요청이 결제
   완료가 되고 **양쪽에** 알림이 가고, 어느 경로로 확정됐는지(승인/대안)가 기록에 남는다
2. **Given** 자동 결제가 실패했다, **When** 실패가 확정된다, **Then** 주는 사람에게 알림이
   가고, **수령자에게는 아무것도 노출되지 않는다** — 주는 사람의 결제 실패는 사적 정보다
3. **Given** 결제 실패 상태다, **When** 주는 사람이 복구 화면을 연다, **Then** 시도 횟수와
   재시도 기한이 보이고, 같은 카드 재시도 / 결제수단 변경 후 재시도를 고를 수 있다
4. **Given** 결제수단을 바꿔 재시도했다, **When** 성공한다, **Then** 결제 완료가 되고 양쪽에
   알림이 간다
5. **Given** 최대 시도 횟수 또는 재시도 기한을 초과했다, **When** 초과가 확정된다, **Then**
   요청이 취소되고 **양쪽에** 고지된다 — 수령자에게는 "결제가 완료되지 않아 취소되었어요"
6. **Given** 어떤 결제 시도든, **Then** 결제 기록이 해당 요청에 연결되어 남는다 — 금액·결과·시각

### User Story 6 - 홈이 액션 허브가 되고 일정·내역이 모인다 (Priority: P2)

홈 최상단에 승인 대기가 임박순으로 뜨고, 다가오는 일정(생일·기념일)과 선물 내역이 모인다.
앱 셸이 4탭 체제로 전환되고 시작 화면이 홈이 된다.

**Why this priority**: 응답 기한이 짧아 승인 대기 노출 위치가 만료율을 좌우하지만,
알림·직접 진입만으로도 US1~US5의 플로우 자체는 성립한다. 그래서 P1들보다 한 단계 뒤다.

**Independent Test**: 승인 대기 1건 이상·일정 1건 이상을 만든 상태로 홈을 열어 배치·정렬·
만료 전환을 확인한다.

**Acceptance Scenarios**:

1. **Given** 내게 승인 대기 요청이 있다, **When** 홈을 연다, **Then** 승인 대기가 **최상단**에
   임박순으로 보인다. 여러 건이면 가장 임박한 1건만 펼치고 나머지는 접는다
2. **Given** 홈에 승인 대기 카드가 떠 있다, **When** 기한이 0이 된다, **Then** 카드가 만료
   상태로 바뀐다 — 홈을 여는 것 자체가 만료 판정 트리거다
3. **Given** 남은 시간이 여러 화면에 보인다(홈·전송 완료·요청 상세·수신·재선택·내역),
   **Then** 모든 화면이 같은 기준 시각으로 같은 값을 보여준다
4. **Given** 내가 일정을 등록·편집한다, **Then** "친구에게 이 일정이 보입니다"가 고지되고,
   매년 반복 일정은 연도와 무관하게 월·일로 매칭된다
5. **Given** 친구의 일정이 있다, **When** 홈·친구 탭을 연다, **Then** 다가오는 일정이 임박순으로
   보인다 — 친구 일정 조회는 취향 열람과 **같은 접근 규칙**을 지난다
6. **Given** 주고받은 선물이 있다, **When** 선물 내역을 연다, **Then** 보낸 것/받은 것 탭,
   진행 중/지난 선물 구분, 대안으로 변경된 건의 라벨이 보인다
7. **Given** M3가 열렸다, **Then** 하단 탭 4개가 전부 활성이고 시작 화면이 친구 탭에서 홈으로
   바뀐다. 마이 탭에 선물 내역·결제수단 메뉴가 노출된다
8. **Given** 위시리스트에 항목을 추가한다, **When** 입력 방식을 고른다, **Then** 기존 텍스트
   입력에 더해 **카탈로그에서 고르기**가 생긴다 — 고른 상품은 취향 항목과 연결된다
9. **Given** gift 관련 알림 6종이 쌓였다, **When** 알림 목록을 연다, **Then** 각 종류가 알아볼
   수 있는 문구로 보이고, 누르면 해당 화면(수신·상세·결과·복구)으로 이동한다

---

### Edge Cases

- **관계 해제 후 진행 중 요청** → 요청 화면은 생성 시점의 스냅샷(상품·수령자 표시명·배송지)만으로
  계속 성립한다. 취향 열람은 즉시 차단 — 거래 화면이 열린다는 것이 취향 접근 권한을 되살리지 않는다
- **해제된 친구의 과거 알림을 누른다** → 취향 카드류는 접근 거부가 정상이다(M2 Edge Case 유지).
  거래 화면(요청 상세·결과)은 스냅샷으로 열린다
- **같은 친구에게 여러 요청이 동시에 존재한다** → 막지 않는다. 수령자 홈은 임박순 1건만 펼치고
  나머지를 접는 것으로 혼란을 줄인다
- **수령자가 앱을 열지 않는다** → 알림이 인앱뿐이므로 짧은 응답 기한 안에 알 방법이 없다.
  시연 기준의 전제이며, 실서비스 배포 시 기한 상향 또는 푸시 도입이 필수다 (화면 명세 갭 7)
- **승인 후 결제 전에 결제수단이 삭제·만료됐다** → 결제 실패 경로로 흘러 재시도(수단 변경)로
  복구한다. 별도 특수 처리를 만들지 않는다
- **요청 금액 이하 상품이 0건이다** → "이 금액대에 고를 수 있는 상품이 없어요. 원래 상품으로
  받으시겠어요?" — 수신 화면으로 복귀시킨다
- **판매 중지된 상품** → 카탈로그·상세 진입은 막되, 이미 만들어진 요청은 스냅샷으로 계속 렌더된다
- **운영 중 응답 기한 설정을 바꾼다** → 이미 뜬 요청은 흔들리지 않는다 — 기한은 생성 시점에
  절대 시각으로 스냅샷됐다
- **결제 처리 중 화면에서 이탈한다** → 결과는 알림으로 전달된다. 사용자를 화면에 붙잡아 두지 않는다
- **만료 화면의 문구** → 수령자를 탓하지 않는다. "확인하지 못했습니다"는 사실 서술까지만

## Requirements *(mandatory)*

### Functional Requirements

#### 카탈로그 · 탐색

- **FR-001**: 시스템은 상품 카탈로그를 제공해야 하며, 판매 중인 상품만 노출해야 한다
- **FR-002**: 사용자는 상품을 이름으로 검색하고 카테고리로 필터링할 수 있어야 한다.
  상품의 카테고리는 **취향 항목과 같은 카테고리 마스터**를 써야 한다
- **FR-003**: 사용자가 받을 친구를 고르면(대상 필터), 그 친구가 `관심 없어요`로 표시한
  카테고리의 상품이 **목록에서 제외**되어야 한다
- **FR-004**: `이미 있어요` 카테고리의 상품은 **제외하지 않고 표시만 구분**해야 한다
- **FR-005**: 상품 상세는 대상 친구가 선택된 경우 취향 매칭 상태 3종(원하는 것 일치 / 이미
  있음 주의 / 관심 없음 차단)을 보여야 하며, `관심 없어요` 일치 시 **선물하기를 비활성**해야 한다
- **FR-006**: 친구 맞춤 추천은 `원하는 것` 매칭을 우선으로, 같은 카테고리 확장을 보조로
  보여야 하며, **어떤 카테고리를 제외했는지 안내**해야 한다
- **FR-007**: 친구 취향을 읽는 모든 조회(대상 필터·매칭 배너·추천)는 활성 친구 관계일 때만
  허용되어야 한다 — M2의 단일 접근 제어 규칙을 우회하는 경로를 만들지 않는다

#### 결제수단

- **FR-008**: 시스템은 카드번호·CVC를 **저장하지 않아야 한다.** 결제대행사가 보관하고,
  시스템은 재결제용 키만 **암호화하여** 보관한다. 화면 표시는 브랜드·마지막 4자리로 한정한다
- **FR-009**: 재결제용 키는 **사용자당 재사용**해야 한다 — 카드 등록은 한 번, 동의는 요청마다
- **FR-010**: 사용자는 결제수단을 등록·조회·삭제할 수 있어야 하며, 등록 화면에는 "카드 정보는
  넌지시에 저장되지 않습니다"를 고지해야 한다
- **FR-011**: 진행 중 요청이 참조하는 수단의 삭제는 **경고 후 허용**하되, 결제 실패 경로로
  이어질 수 있음을 고지해야 한다
- **FR-012**: 만료된 수단은 구분 표시하고 재등록을 유도해야 한다

#### 요청 생성 · 동의

- **FR-013**: 요청 생성은 다음을 전부 통과해야 한다 — ① 활성 친구 관계 ② 주는 사람의 활성
  결제수단 존재 ③ 상품이 수령자의 `관심 없어요` 카테고리가 아님 ④ 자기 자신이 아님.
  화면에서 이미 차단된 조건도 **생성 시점에 다시 검증**한다
- **FR-014**: 재결제 동의는 **별도 화면**에서 받아야 하며, 동의 전 전송 버튼은 비활성이어야
  한다. 문구에는 요청 금액 상한(숫자) · 차액 미청구·미환급 · 결제 결과 고지가 담겨야 한다
- **FR-015**: 시스템은 동의 시각과 **동의 문구 버전**을 요청에 기록해야 한다. 문구를 수정하면
  반드시 버전을 올린다 — 과거 동의가 무엇이었는지 항상 복원 가능해야 한다
- **FR-016**: 요청은 생성 시점에 상품 정보 · 수령자 표시명 · 응답 기한(**절대 시각**)을 자기
  안에 스냅샷해야 한다. 진행·완료된 요청의 표시는 스냅샷만으로 성립해야 한다
- **FR-017**: 응답 기한은 설정값으로 조정 가능해야 하며(시연 기본 5분), 이미 생성된 요청의
  기한은 설정 변경의 영향을 받지 않아야 한다
- **FR-018**: 요청 생성 성공 시 수령자에게 알림이 가야 한다
- **FR-019**: 주는 사람은 **응답 대기 상태에서만** 요청을 취소할 수 있어야 한다

#### 수령자 응답

- **FR-020**: 수령자의 선택지는 승인 / 대안 제시 / 무응답 셋뿐이어야 한다. **거절 상태와 거절
  버튼을 만들지 않는다**
- **FR-021**: 대안 상품의 금액은 **최초 요청 금액 이하**여야 한다. 화면 필터와 저장 계층
  양쪽에서 강제한다 — 화면은 첫 번째 방어선, 저장 거부가 마지막 방어선이다
- **FR-022**: 대안 관련 기록(상품·스냅샷·금액)은 **전부 있거나 전부 없어야** 한다
- **FR-023**: 대안 재선택 목록은 수령자 본인의 `원하는 것` 매칭을 우선 노출해야 한다
- **FR-024**: 대안 확정 **전에** "주는 사람에게 알려진다"와 차액 미청구를 고지해야 하며,
  확정 시 주는 사람에게 알림이 가고 요청 상세에 원래 상품 → 최종 상품 대조와
  차액 미청구 문구가 보여야 한다
- **FR-025**: 배송지는 수령자가 **이 거래에** 제공하는 값이며 요청 안에만 저장된다. 프로필
  공용 배송지를 만들지 않는다. "이 주소는 이 선물에만 사용됩니다"를 고지한다
- **FR-026**: 만료된 요청에는 어떤 응답도 성립하지 않아야 한다. 조회와 응답 양쪽이 진입
  시점에 만료 여부를 판정한다
- **FR-027**: 같은 요청에 응답·결제 시도가 겹쳐도(더블탭·동시 요청·재시도) 결제는 **정확히
  1회**만 시도되어야 한다

#### 결제 실행 · 실패 복구

- **FR-028**: 승인·대안 어느 경로든 확정 즉시 **추가 조작 없이** 자동 결제가 실행되어야 한다
- **FR-029**: 결제 성공 시 어느 경로로 확정됐는지(승인/대안)를 기록에 남기고 **양쪽에**
  알림을 보내야 한다
- **FR-030**: 결제 실패 시 주는 사람에게 알리고 재시도를 허용해야 한다 — 같은 수단 재시도와
  결제수단 변경 후 재시도 양쪽. **수령자에게는 실패 진행 상황을 노출하지 않는다**
- **FR-031**: 재시도는 최대 시도 횟수와 재시도 기한(둘 다 설정값, 기본 3회 · 24시간) 안에서만
  허용되어야 하며, 복구 화면에 현재 시도 횟수와 기한이 보여야 한다
- **FR-032**: 상한 초과 시 요청은 취소되고 **양쪽에 고지**되어야 한다. 수령자 고지("결제가
  완료되지 않아 취소되었어요")는 누락될 수 없다 — 승인까지 해놓고 소식이 끊기는 것이 최악이다
- **FR-033**: 모든 결제 시도는 금액·결과·시각과 함께 기록되어야 하며, 각 기록은 정확히
  하나의 거래(선물 요청)에 연결되어야 한다

#### 만료

- **FR-034**: 만료는 배치 없이 **조회·응답 시점의 지연 평가**로 판정한다 — 화면을 여는 것이
  판정 트리거이며, 판정 오차가 없다
- **FR-035**: 만료가 확정되는 시점에 주는 사람에게 만료 알림이 생성되어야 한다
- **FR-036**: 만료 안내 문구는 수령자를 탓하지 않는 사실 서술이어야 한다

#### 알림

- **FR-037**: M2의 알림 목록에 gift 6종이 추가되어야 한다 — 요청 도착(수령자) · 대안
  제시(주는 사람) · 결제 완료(양쪽) · 결제 실패(주는 사람) · 결제 취소(수령자) · 만료(주는
  사람). 각 알림은 알아볼 수 있는 문구와 해당 화면으로의 이동을 가져야 한다

#### 홈 · 일정 · 내역

- **FR-038**: 홈은 승인 대기를 **최상단**에 임박순으로 배치해야 하며, 여러 건이면 가장 임박한
  1건만 펼치고 나머지는 접는다
- **FR-039**: 응답 기한 카운트다운은 모든 화면에서 **같은 기준 시각**으로 같은 값을 보여야 한다
- **FR-040**: 사용자는 일정(생일·기념일·기타)을 등록·편집·삭제할 수 있어야 하며, 매년 반복
  일정은 연도 무시 월·일 매칭이어야 한다. "친구에게 이 일정이 보입니다"를 고지한다
- **FR-041**: 친구 일정 조회는 취향 열람과 **같은 접근 규칙**(활성 친구만)을 따라야 한다
- **FR-042**: 선물 내역은 보낸 것/받은 것 · 진행 중/지난 선물을 구분하고, 대안으로 변경된
  건에 라벨을 보여야 한다. 관계 해제 후에도 스냅샷으로 렌더되어야 한다
- **FR-043**: M3 공개와 함께 앱 셸이 4탭 전부 활성으로 전환되고 시작 화면이 홈이 되어야
  한다. 마이 탭에 선물 내역·결제수단 메뉴가 노출된다
- **FR-044**: 위시리스트 추가에 **카탈로그에서 고르기** 경로가 생겨야 하며, 고른 상품은 취향
  항목과 연결된다. 기존 텍스트 입력 경로는 유지한다

#### 측정

- **FR-045**: "선물 승인률"(대안 제시 없이 승인된 비율)이 별도 이벤트 수집 없이 확정 경로
  기록의 집계만으로 측정 가능해야 한다

### Key Entities *(include if feature involves data)*

- **Product (상품)**: 시드 카탈로그의 상품. 이름·가격·이미지·판매 여부, 그리고 **취향 항목과
  같은 마스터**를 가리키는 카테고리. 이 공유가 "어긋난 선물 걸러내기"를 조인 한 번으로 만든다
- **PaymentMethod (결제수단)**: 사용자의 재결제용 키(암호화)와 표시용 정보(브랜드·마지막
  4자리), 상태(활성/만료/삭제). 카드 원본 정보는 담지 않는다
- **GiftRequest (선물 요청)**: 이 마일스톤의 중심. 주는 사람·수령자, 상태(대기/결제 중/완료/
  실패/만료/취소), 확정 경로(승인/대안), 상품 스냅샷, 요청 금액, 대안 3값(전부 또는 전무),
  수령자 표시명 스냅샷, 배송지 스냅샷, 동의 시각·버전, 응답 기한(절대 시각), 재시도
  기한·횟수. **거절 상태가 없다.** 진행·표시가 스냅샷만으로 자립한다
- **Payment (결제 기록)**: 결제 시도의 결과 — 금액·상태·시각·대행사 거래 식별자. 정확히
  하나의 거래에 연결된다 (M4의 펀딩 참여도 같은 기록을 쓰게 된다)
- **Event (일정)**: 일정의 주체·종류(생일/기념일/기타)·이름·날짜·매년 반복 여부. 생일을
  사용자 필드가 아니라 일정으로 통일한다 — 홈이 "다가오는 일정" 하나의 축으로 돈다
- **Notification (알림)** — *M2에서 존재*: 종류에 gift 6종이 추가된다. 구조는 바뀌지 않는다
- **TasteItem (취향 항목)** — *M1에서 존재*: 카탈로그 상품을 가리키는 연결(선택)이 추가된다.
  위시리스트의 "카탈로그에서 고르기"가 이 연결을 쓴다
- **User · Friendship** — *M1·M2에서 존재*: 읽기만 한다. 구조를 바꾸지 않는다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 수령자가 승인 후 배송지 입력을 마치면 **추가 조작 0회**로 결제가 완료되고,
  양쪽 모두 결과를 알림에서 확인할 수 있다 — 승인·대안 양쪽 경로 모두
- **SC-002**: 같은 요청에 동시·중복 응답을 아무리 넣어도 청구는 **정확히 1회**다 —
  중복 청구 0건
- **SC-003**: `관심 없어요` 카테고리 상품의 선물 시도가 목록·상세·생성 세 지점 전부에서
  차단된다 — 우회 성공 0건
- **SC-004**: 만료된 요청에 대한 응답 성공이 0건이다 — 별도 배치 없이, 진입 즉시 판정된다
- **SC-005**: 대안 금액이 요청 금액을 초과해 저장된 건이 0건이다
- **SC-006**: 결제 실패 후 사용자 조작 2회 이내(수단 변경 포함)로 재시도가 완료되고, 상한
  초과 취소 시 수령자 고지 누락이 0건이다
- **SC-007**: 동의 없이 생성된 요청이 0건이고, 모든 요청에 동의 시각·문구 버전이 기록돼 있다
- **SC-008**: 카드번호·CVC가 시스템 어디에도 저장되지 않는다 — 저장소·로그 포함
- **SC-009**: 관계 해제 후에도 진행 중·완료 거래 화면이 오류 없이 성립하고, 취향 접근 차단은
  100% 유지된다
- **SC-010**: 폭 360px에서 M3의 모든 화면(18개)이 가로 스크롤 없이 동작한다
- **SC-011**: "선물 승인률"이 별도 이벤트 수집 없이 쿼리 한 번으로 나온다

## Assumptions

### 확정된 것을 그대로 따른 것

- **거절 상태를 만들지 않는다** (도메인 모델 §5). 승인 / 대안 제시 / 무응답뿐이며, 이 스펙은
  그 결정을 재검토하지 않는다
- **자동 결제는 사전 동의로 위임받은 재결제다** (확정 결정 4-1). 대안 제시 시에도 즉시 자동
  결제하고 사후 고지한다
- **카드 등록은 한 번, 동의는 요청마다** (도메인 모델 §5). 결제수단 재사용이 원칙이다
- **거래는 스냅샷으로 자립한다** (constitution 원칙 IV · D3). 관계 해제 예외를 조회마다
  분기하지 않고, 생성 시점 복사로 해결한다
- **만료는 지연 평가다** (도메인 모델 §8). cron·배치를 만들지 않는다. 다만 만료 *알림*은
  화면 명세(SCR-M3-02 · M3 플로우)에 있으므로, 지연 평가가 만료를 확정하는 바로 그 지점에서
  생성한다 — 도메인 모델 §8의 "만료 알림은 범위 밖"은 *스케줄러 기반* 알림을 배제한 것으로 읽는다
- **설정값은 전부 조정 가능하게** (도메인 모델 §9) — 응답 기한·재시도 기한·최대 시도 횟수.
  생성 시점 절대 시각 스냅샷으로 운영 중 변경과 격리한다
- **결제대행사는 PortOne** (도메인 모델 §5). 연동 수준은 **혼합으로 확정**(Clarifications Q1) —
  시뮬레이션 기본 + 같은 인터페이스 뒤 실연동, E2E는 항상 시뮬레이션

### 기본값으로 채택한 것 (열린 항목의 권장안)

- **캘린더는 목록형으로 확정** (Clarifications Q2) — 화면 명세가 이미 목록형으로 설계했고(§13
  갭 4), 생일은 1인당 연 1회라 월간 그리드의 밀도가 낮다. 별도 월간 뷰를 만들지 않는다
- **대안 제시 버튼 문구는 "다른 것도 좋아요"로 확정** (Clarifications Q3) — 화면 명세
  SCR-M3-12의 제안을 그대로 채택했다
- **동의 문구 v1은 SCR-M3-09 초안으로 확정** (Clarifications Q4) — 이 문구가 v1이고, 이후
  수정마다 버전이 올라간다

### 범위 밖

- **푸시·외부 발송** — M2와 동일, 인앱만. 짧은 응답 기한과의 긴장은 시연 기준의 전제로 수용한다
- **실물 주문·배송 처리** — 결제 완료까지가 범위다. 자체 커머스·물류는 PRD Out of scope
- **프로필 기본 배송지** — 의도된 비용(화면 명세 갭 8). 관계 해제 후 주소가 남는 경로를 만들지 않는다
- **추천 랭킹 고도화** — 카테고리 일치 + 가격대 정렬까지만 (화면 명세 갭 9)
- **상품 검색 고도화** — 이름 부분 일치로 충분 (화면 명세 갭 10)
- **관리자 도구** (상품 시드 관리 화면) — 시드 데이터로 대체
- **펀딩** — M4 (`specs/004-*`)

### 그 밖의 가정

- M2 완료 상태를 전제한다 — 활성 친구 관계·알림 목록·접근 제어 단일 규칙이 이미 존재한다
- 상품 카탈로그는 시드 30~50건으로 채우며, 시연 시나리오 커버 조건(원하는 것 일치 · 이미
  있음 · 관심 없음 · 요청가보다 싼 대안 각 1건 이상)을 만족해야 한다
- E2E 검증은 계정 2개(주는 사람·수령자)로 가능하다 — 3계정은 M4부터
