## Problem

선물은 주는 사람이 아는 만큼만 좋아진다. 그런데 상대의 취향을 알 방법이 마땅치 않다. 물어보면 "아무거나"라는 답이 돌아오고, 짐작으로 고르면 이미 가진 것과 겹치거나 결국 쓰지 않는 물건이 된다.

받는 쪽도 사정은 같다. 원하는 것이 분명히 있어도 그것을 전할 자리가 없어, 필요 없는 선물이 쌓인다.

넌지시는 **선물 받는 사람(나 또는 타인)의 맞춤 취향**을 기록하고 전달해, 이 어긋남을 양쪽에서 줄인다.

## Evidence

- `Assumption — needs validation via 사용자 인터뷰` : "선물이 취향과 어긋나 안 쓰게 되는 일이 얼마나 자주 일어나는가"에 대한 정량 근거가 없다.
- `Assumption — needs validation via 사용자 인터뷰` : "사람들이 자신의 맞춤 취향을 선물에 쓸 만큼 **상세하게** 기록할 의향이 있는가" — 이 제품의 **가장 위험한 가정**이다.
- `Assumption — needs validation via 경쟁 서비스 조사` : 위시리스트 서비스는 존재하지만, "이미 있는 것 / 필요 없는 것"까지 함께 담는 서비스는 아직 확인되지 않았다.

> ⚠️ 이 섹션이 비어 있는 것이 현재 PRD의 최대 약점이다. 지인 15~20명 인터뷰로 채울 수 있으며, 그 전까지 성공 지표의 목표 수치는 확정할 수 없다.

## Users

넌지시는 **양면 서비스**다. 받는 쪽과 주는 쪽이 모두 있어야 가치가 발생한다.

### 받는 쪽

- 내가 진짜 원하는 선물을 받고 싶은 사람
- 필요 없는 선물들이 쌓여서 골치 아파본 사람

### 주는 쪽

- 상대방이 진짜 원하는 선물을 주고 싶은 사람
- 상대방의 취향을 몰라서 어떤 선물을 할지 감이 안 오는 사람

> 인구통계가 아니라 **상황(need-state)** 으로 정의한다. 나이·직업이 아니라 위 네 가지 상태에 있는 사람이 대상이다.

- **Not for**: 익명 관계, 불특정 다수 대상 선물, 기업 판촉·단체 선물.
  넌지시는 **이름과 관계가 있는 1:1 및 1:n 선물**만 다룬다.

## Hypothesis

We believe **선물 받는 사람의 맞춤 취향을 기록하고 친구에게 전달하는 것**이
**"원하지 않는 선물을 주고받는" 문제를 해소**할 것이다 —
**원하는 걸 받고 싶은 사람과, 제대로 주고 싶은 사람**에게.

We'll know we're right when **`TBD — 성공 지표 확정 필요`**.

## Scope

### MVP

맞춤 취향을 남기고, 친구에게 전달되고, 그 취향에 근거해 선물이 결정되는 **최소 루프 1회**를 완성한다.

| # | 능력 | 설명 |
|---|---|---|
| 1 | **맞춤 취향 프로필** | 아래 세 종류의 항목으로 구성 |
| 2 | **친구 추가 요청 링크** | 링크 수신자는 가입·친구 수락 후 상세 취향을 열람 |
| 3 | **친구 목록 + 다가오는 일정** | 홈을 관계 중심 액션 허브로 만드는 최소 데이터 |
| 4 | **선물 승인 / 대안 제시 플로우** | A 선택 → B 승인 시 결제 / B가 대안 제시 시 요청 금액 이하로 재선택 후 결제 |
| 5 | **공동 펀딩** | 고가 선물의 가격 상한을 올리는 장치 |

**맞춤 취향 프로필의 구성**

| 항목 | 입력 방식 | 필수 |
|---|---|---|
| 원하는 것 | 위시리스트 | 선택 |
| 이미 있는 것 · 필요 없는 것 | **대분류 선택**(예: "텀블러"). 상세 지정(예: "스타벅스 텀블러")은 **사용자 재량** | 온보딩 필수 |
| 취향 서술 | 자유 입력 | 선택 |

> 대분류는 **잘못된 선물을 걸러내고**, 상세·서술은 **추천의 정확도를 올린다.** 둘은 용도가 다르므로 입력 강제 수준도 다르게 둔다.

### 확정된 정책 결정

**선물 승인 플로우**

| 항목 | 결정 |
|---|---|
| 결제 시점 | **수령자 확정 이후** — 요청 시점 결제 없음 |
| 대안 제시 시 금액 | 최초 요청 금액 **이하**. 차액은 청구하지 않음 |
| 대안 제시 사실 고지 | **주는 사람에게 알린다** |
| 승인 요청 만료 | **5분** (시연·테스트 기준). **설정 가능해야 하며 실서비스 배포 시 조정** |
| 사전 동의 | 결제 전 "요청 금액 이하의 상품으로 재결제될 수 있음"에 대한 **명시적 동의 화면** 필요 |

**펀딩**

| 항목 | 결정 |
|---|---|
| 개설 주체 | **주최자, 수령자 모두 가능** |
| 목표 구조 | 목표 금액 + **최소 달성선** 설정 |
| 최소 달성선 미만 | **펀딩 취소** — 참여금 전액 환불 |
| 최소 달성선 이상 ~ 목표 미만 | **주최자가 차액 부담** |
| 목표 초과 | 초과 참여 불가 (캡) |
| 1인 최대 참여액 | **제한 없음** |
| 지분 공개 범위 | **주최자 + 수령자**에게 공개 |

**하단 네비게이션 (4탭)**

| 탭 | 내용 |
|---|---|
| 홈 | 다가오는 일정 · 승인 대기 · 진행 중 펀딩 |
| 친구 | 친구 목록 · 취향 카드 · **취향에 맞는 선물 추천** |
| 선물 | 검색 · 카테고리 |
| 마이 | 내 취향 · 선물 내역 · 펀딩 내역 · 설정 |

### Constraints (팀 결정)

- 결제는 **포트원(PortOne) 연동 수준**까지. PG 실계약·정산은 범위 밖.
- 반응형(데스크톱/태블릿/모바일), **모바일 기준** 설계.
- "반려" 대체 문구는 **개발 중 확정** — 요구사항은 "거절이 아닌 대안 제시로 읽혀야 한다".

### Out of scope (MVP)

| 항목 | 이유 |
|---|---|
| 포인트·자체 화폐 발행 | 선불전자지급수단 규제. 차액 미청구 정책으로 불필요해짐 |
| 최저가 비교·가격 추적 | 별도 제품 규모. 크롤링 법적 리스크 |
| 자체 커머스·물류 | 교환·반품을 직접 소유하지 않음 |
| 소셜 피드 | 관계는 1:1·1:n에 한정 |
| 가입 없는 취향 열람 | 개인정보 보호를 위해 **친구 추가 링크로 대체** (Risks R1) |

## Future (MVP 이후 구현 예정)

MVP에서 제외하되 **폐기가 아니라 연기**한다. 아래 두 기능은 맞춤 취향 데이터와 선물 이력이 쌓인 뒤에 의미가 생긴다.

| 기능 | 내용 | 선행 조건 |
|---|---|---|
| **경조사** | 축의금·부의금 기록, 주고받은 금액 참고 | 관계 데이터(친구 목록)와 이력이 먼저 쌓여야 함 |
| **가계부** | 선물·경조사 지출 관리 | 선물 결제 이력이 먼저 쌓여야 함 |

> 두 기능 모두 **기록 자동화**(문자·청첩장 파싱 등) 없이는 수기 입력 부담으로 사용률이 낮아진다. 착수 시점에 함께 검토할 것.

## Open Questions

- [ ] **타인의 취향을 대신 등록할 수 있는가** — Problem의 "나 또는 타인"이 (a) 관점의 차이일 뿐인지, (b) 미가입 친구의 취향을 내가 기록하는 기능인지. (b)라면 범위가 크게 늘어난다
- [ ] **캘린더의 위치** — 친구 탭에서 빠졌으므로, 홈의 "다가오는 일정"으로 충분한지 별도 월간 뷰가 필요한지
- [ ] **양면 중 어느 쪽을 먼저 확보하는가** — 받는 쪽 먼저가 자연스럽지만(취향 데이터가 자산), 명시적 결정 필요
- [ ] **Why now?** — 지금 이 제품을 만들 이유
- [ ] **성공 지표의 목표 수치** — Evidence 확보 후 확정
- [ ] **수령자가 펀딩을 개설한 경우 차액 부담자는 누구인가** (Risks R3)
- [ ] 맞춤 취향을 **친구별로 다르게 공개**할 수 있어야 하는가
- [ ] 친구 관계 해제 시 이미 열람한 취향 정보의 처리

## Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | **콜드스타트** — 공유 링크를 친구 추가 요청으로 바꾸면서 "가입 없이 열람" 방어책이 사라짐. 양쪽 모두 가입해야 가치가 발생 | 높음 | 높음 | 링크 열람 시 **미리보기**(이름 + 대표 태그 2~3개)까지는 비가입 노출, 상세는 친구 수락 후. 가입 동기를 만들면서 완전 차단은 피함 |
| R2 | **맞춤 취향이 대분류에서 멈춤** — 상세·서술이 비면 "텀블러 빼고" 수준의 필터에 그쳐, 평범한 위시리스트로 회귀 | 높음 | 높음 | 가입 시 강제하지 않고 선물 수령 후 후기로 환류. 마일스톤 1 직후 **상세 작성률을 즉시 측정**해 가정을 검증 |
| R3 | **수령자 개설 펀딩의 차액 부담 주체 불명** — 개설자=수령자이면 자기 선물의 차액을 자기가 내는 구조 | 중간 | 중간 | Open Question으로 해소. 미해소 시 마일스톤 4에서 개설 주체를 주최자로 한정 |
| R4 | **1인 참여액 무제한 + 초과 캡** — 첫 참여자가 전액을 채우면 이후 참여가 불가능해져 펀딩의 의미가 사라짐 | 중간 | 중간 | **잔여 금액 실시간 표시**와 참여 전 확인 단계로 완화. 재발 시 정책 재검토 |
| R5 | **지분 공개로 인한 관계 마찰** — 수령자가 참여자별 금액을 모두 확인 가능 | 중간 | 중간 | 정책 유지하되 참여 시점에 "수령자에게 금액이 공개됩니다" 명시 |
| R6 | **대안 제시 고지의 감정 비용** — 주는 사람이 자신의 선택이 받아들여지지 않았음을 알게 됨 | 중간 | 중간 | 문구를 거절이 아닌 대안 제시로 설계. 결제 고지로 어차피 드러나므로 은폐는 선택지가 아님 |
| R7 | **선물 탭의 사용률** — 친구 탭에 취향 기반 추천이 들어가면서 자유 검색 탭의 진입 동기가 약해짐 | 중간 | 낮음 | 마일스톤 3 이후 탭별 진입률 측정. 낮으면 선물 탭을 홈·친구 하위로 흡수 |
| R8 | **결제 승인 지연 구조** — 요청 후 확정까지 시간차로 결제수단 상태가 변할 수 있음 | 중간 | 낮음 | 만료 기한(5분, 설정 가능)과 결제 실패 시 재요청 플로우 정의 |
| R9 | **취향 데이터의 민감성** — 알러지(건강), 사이즈(신체), 가격대(소득 추정)가 한 프로필에 모임 | 낮음 | 높음 | 친구 관계 기반 접근 제어. 조회 로그. 항목별 공개 범위는 Open Question |
