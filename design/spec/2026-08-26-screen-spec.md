## 0. 이 문서를 읽는 법

### 화면 ID 체계

```
SCR-M{마일스톤}-{일련번호}
```

마일스톤 번호는 PRD의 Delivery Milestones와 도메인 모델 §11을 그대로 따른다. **순서를 바꾸면 취향이 비어 있는 화면을 시연하게 된다**는 제약이 화면 ID에도 그대로 걸려 있다.

| 접두 | 범위 | 근거 |
|---|---|---|
| `SCR-M0` | 진입 · 인증 · 앱 셸 | 마일스톤 이전의 전제 |
| `SCR-M1` | 맞춤 취향 | M1 |
| `SCR-M2` | 친구 · 초대 링크 | M2 |
| `SCR-M3` | 선물 요청 · 응답 · 결제 | M3 |
| `SCR-M4` | 펀딩 | M4 |
| `SCR-C` | 공통 상태 · 패턴 | 전 구간 |

### 와이어프레임 표기

순수 ASCII로 그린다. 박스 드로잉 문자는 CJK 폰트에서 폭이 흔들려 정렬이 깨진다.

| 표기 | 뜻 |
|---|---|
| `[ 라벨 ]` | 주 액션 버튼 (Primary) |
| `( 라벨 )` | 보조 액션 버튼 (Secondary / Ghost) |
| `<` `>` | 뒤로 가기 / 다음 단계·상세 이동 |
| `____` | 텍스트 입력 필드 |
| `[o]` | 아바타 · 이미지 썸네일 |
| `[v]` `[ ]` | 선택됨 / 선택 안 됨 |
| `(*)` `( )` | 라디오 선택됨 / 안 됨 |
| `====` | 진행 바 |
| `~~~~` | 스켈레톤 · 로딩 |
| `>>` | 그 화면에서 나가는 전이 |

### 각 화면 명세의 구성

| 항목 | 내용 |
|---|---|
| **진입** | 어느 화면·이벤트에서 들어오는가 |
| **와이어프레임** | 기본 상태 1개. 분기가 크면 변형을 함께 그린다 |
| **요소** | UI 요소 / 데이터 소스(엔티티.필드) / 액션 |
| **상태 · 예외** | 빈 상태, 실패, 만료 등 |
| **접근 제어** | 도메인 모델 §7 규칙의 화면 적용 |
| **근거** | PRD · 도메인 모델의 어느 결정에서 나왔는가 |

**데이터 소스가 비어 있는 요소는 화면에 두지 않는다.** 도메인 모델에 없는 필드를 요구하는 UI는 §13(갭과 열린 항목)에 올린다.

## 2. 네비게이션 구조

PRD의 하단 4탭을 그대로 따른다. product-lens v3 §5의 수정안(홈 = 액션 허브, 캘린더 흡수, "싫은 선물" → "내 취향")은 이미 PRD에 반영되어 있다.

```
앱 셸 (SCR-M0-04)
 |
 +-- [홈]   SCR-M3-01  다가오는 일정 / 승인 대기 / 진행 중 펀딩
 |            +-- SCR-M3-02  알림 목록
 |            +-- SCR-M3-12  요청 수신 (받는 사람)
 |            +-- SCR-M4-04  펀딩 상세
 |            +-- SCR-M3-17  일정 등록/편집
 |
 +-- [친구] SCR-M2-01  친구 목록 + 다가오는 일정
 |            +-- SCR-M2-02  링크 발급/공유
 |            +-- SCR-M2-03  링크 관리
 |            +-- SCR-M2-06  친구 상세 - 취향 카드
 |                  +-- SCR-M3-05  맞춤 추천
 |                  +-- SCR-M2-07  친구 해제
 |
 +-- [선물] SCR-M3-03  검색 / 카테고리
 |            +-- SCR-M3-04  상품 상세
 |                  +-- SCR-M3-08  선물 요청 시작
 |                  +-- SCR-M4-01  펀딩 개설 시작
 |
 +-- [마이] SCR-M1-06  마이 홈
              +-- SCR-M1-07  내 취향
              +-- SCR-M3-18  선물 내역
              +-- SCR-M4-08  펀딩 내역
              +-- SCR-M3-07  결제수단 관리
```

### 탭 밖에서 열리는 화면

| 화면 | 진입 |
|---|---|
| SCR-M0-01~03 | 비로그인 |
| SCR-M1-01~05 | 가입 직후 강제 진입. 완료 전까지 탭 접근 불가 |
| SCR-M2-04~05 | **외부 링크** — 앱 셸 밖의 독립 라우트 |

> **SCR-M2-04(미리보기)가 앱 셸 밖에 있는 것이 핵심이다.** 비가입자가 보는 유일한 화면이고, R1(콜드스타트)의 방어선이 여기 하나뿐이다. 여기에 로그인 벽을 세우면 링크가 유통 채널로 기능하지 못한다.

## 3. 화면 흐름 — 마일스톤별 핵심 경로

### M1 — 맞춤 취향을 남긴다

```
SCR-M0-01 랜딩
   >> SCR-M0-02 로그인/가입
   >> SCR-M0-03 기본 프로필
   >> SCR-M1-01 온보딩 인트로
   >> SCR-M1-02 카테고리 선택        [필수 - 1건 이상]
   >> SCR-M1-03 have/unwanted 구분   [상세는 재량]
   >> SCR-M1-04 취향 서술            [skip 가능]
   >> SCR-M1-05 완료 ................. TasteProfile.onboarded_at 설정
   >> SCR-M3-01 홈
```

**완료 판정**(도메인 모델 §11-1): `kind IN ('have','unwanted')` 항목이 1건 이상이면 `onboarded_at`이 찍힌다. SCR-M1-04는 skip해도 온보딩이 끝난다.

### M2 — 친구에게 취향이 전달된다

```
[발급자]                          [수신자]
SCR-M2-01 친구 탭
   >> SCR-M2-02 링크 발급
        --- 카톡 등으로 전달 --->  SCR-M2-04 미리보기 (비가입)
                                       |
                            +----------+----------+
                            |                     |
                     [이탈: 가입 안 함]    [ 넌지시 시작하기 ]
                                                  |
                                          SCR-M0-02 로그인/가입
                                                  |
                                          SCR-M1-01~05 온보딩
                                                  |
                                          SCR-M2-05 친구 성사   <-- 승인 단계 없음
                                                  |
   <-- friend_joined_via_link 알림 ---------------+
                                                  |
                                          SCR-M2-06 상대 취향 열람
```

**미리보기 → 가입 구간이 이 제품의 퍼널 병목이다.** PRD 성공 지표 "친구 추가 링크 → 가입 전환율"이 정확히 이 화살표를 측정한다.

### M3 — 선물이 수령자 확인을 거쳐 결정된다

```
[주는 사람 A]                                    [받는 사람 B]
SCR-M2-06 / SCR-M3-05  친구 취향 -> 상품
   >> SCR-M3-04 상품 상세
   >> SCR-M3-06 결제수단 등록   [없으면 여기서 막힌다]
   >> SCR-M3-08 요청 확인
   >> SCR-M3-09 재결제 동의     [필수]
   >> SCR-M3-10 전송 완료
        --- gift_request_received --->  SCR-M3-12 요청 수신
                                             |
                              +--------------+--------------+--------------+
                              |              |                             |
                        [ 승인 ]      [ 다른 것도 좋아요 ]            무응답
                              |              |                             |
                              |       SCR-M3-13 재선택                     |
                              |       (<= requested_amount)                |
                              |              |                             |
                              +------+-------+                             |
                                     |                                     |
                              SCR-M3-14 배송지                             |
                                     |                                     |
                              [자동 결제 - 빌링키]                         |
                                     |                                     |
                     +---------------+---------------+                     |
                     |                               |                     |
                  성공                             실패            respond_due_at 초과
                     |                               |                     |
   <- gift_paid -----+       <- gift_payment_failed -+                     |
   SCR-M3-15 완료             SCR-M3-16 복구           <- gift_expired -----+
                                     |                 SCR-M3-15 만료
                          [재시도] / [기한 초과 -> cancelled]
                                     |
                        gift_cancelled_by_payment -> B에게도 고지
```

**화면에 "거절" 버튼이 없다.** 도메인 모델이 `declined` 상태를 만들지 않은 것이 그대로 UI 제약이 된다. 수령자의 선택지는 `승인` / `대안 제시` / `무응답` 셋뿐이다.

### M4 — 고가 선물을 여럿이 함께 준비한다

```
SCR-M3-04 상품 상세
   >> SCR-M4-01 대상 선택
        |
   +----+-----------------------------+
   |                                  |
개설자 != 수령자                 개설자 == 수령자
   |                                  |
SCR-M4-02 목표 + 달성선          SCR-M4-02 목표만
   |                             (min = goal 고정, 입력 잠금)
SCR-M4-03 차액 동의                   |
   |                                  |
   +----------------+-----------------+
                    |
             SCR-M4-04 펀딩 상세  <--- 참여자 진입
                    |
             SCR-M4-05 참여 금액 + 공개 고지
                    |
             SCR-M4-06 예약 -> 결제
                    |
              [마감 또는 goal 도달]
                    |
        +-----------+-----------+
        |                       |
  paid합 >= min           paid합 < min
        |                       |
  succeeded               failed
        |                       |
  차액 자동 결제           전액 환불
        |                       |
  settled                 SCR-M4-07 (미달 안내)
        |
  SCR-M4-07 (성사 안내)
```

### 4.0 브리프가 고정한 것 / 고정하지 않은 것

레퍼런스 6장 중 **4장이 "사이드컬러" 예시**다. 브리프가 색을 축으로 잡고 있다는 뜻이므로, 색은 레퍼런스를 따르고 해석하지 않는다.

| 레퍼런스에서 반복되는 것 | 판정 |
|---|---|
| 딥 그린 필드 + 크림 종이 배경 | **고정** — 4장 전부 |
| 애시드 시트론(형광 레몬)이 **면적으로** 쓰임 | **고정** — 프레임·측면 필드·전면 섹션. 작은 점으로 쓰인 예가 한 장도 없다 |
| 큰 라운드(24~48px) 컬러 블록 | **고정** |
| 필 버튼 + 원형 화살표 배지 | **고정** |
| 고대비 세리프 디스플레이, 대문자·자간 확장 | **부분 채택** — 아래 4.2 참조 |
| 자연물 사진(잔디·잎·나무) | 참고만 — 넌지시는 상품 이미지가 주다 |

**레퍼런스가 답하지 않는 것**: 레퍼런스는 전부 골프클럽·사우나·음료·컨퍼런스의 **랜딩 페이지**다. 넌지시는 카운트다운·결제 동의·펀딩 게이지가 도는 **거래형 모바일 앱**이다. 그래서 다음은 그대로 옮기지 않는다.

| 옮기지 않는 것 | 이유 |
|---|---|
| 대문자 자간 확장 세리프를 본문에 사용 | 한글에 대문자가 없고, 10~14px 한글 세리프는 판독이 무너진다 |
| 전면 사진 히어로 | 홈은 액션 허브다(§8 SCR-M3-01). 사진이 승인 대기를 밀어낸다 |
| 마케팅 스케일 타입(48px+ 헤드라인) | 모바일 거래 화면의 정보 밀도와 충돌 |

### 4.1 디자인 명제

> **넌지시 = 드러내지 않고 놓아둔다.**

이름이 방식(어떻게 전하나)을 가리킨다는 지적은 product-lens v3 §0에 이미 있다. 비주얼이 그 방식을 실행한다. **정보를 선언하지 않고 놓아두는 화면** — 이것이 아래 시그니처(4.4)의 근거다.

### 4.2 색

`.pen`에 토큰이 두 벌 겹쳐 있다(구: `bg`/`forest`/`white`/`font-*`, 신: `cream`/`green`/`sage`/`surface`/`accent`). **한 벌로 정리한다.** 값은 현재 파일의 최신 선택을 따른다.

| 토큰 | 값 | 역할 | 쓰지 않는 곳 |
|---|---|---|---|
| `paper` | `#F5F3EE` | 앱 배경 | 카드 표면 |
| `card` | `#FFFFFF` | 카드·시트 표면 | 배경 |
| `ink` | `#183024` | 본문·제목 | — |
| `muted` | `#687067` | 보조 텍스트·캡션 | **14px 미만 금지** (4.6 대비 참조) |
| `line` | `#D6DDD0` | 헤어라인·구분선 | 텍스트 |
| `forest` | `#1B3A28` | 최심층 면 — 하단 네비, 강조 블록 | 본문 텍스트 |
| `green` | `#2D5E3A` | 주 액션(버튼·링크·게이지) | 넓은 배경 |
| `sage` | `#4A6B52` | 3차 면·비활성 그린 | 본문 텍스트 |
| `citron` | `#F2F15A` | **사이드컬러 — 면으로만** | 텍스트·아이콘·1px 선 |
| `alarm` | `#F2785C` | **실패·만료 전용** | 장식·강조·브랜드 |

#### 두 가지 색 규칙

**규칙 1 — 시트론은 면이지 점이 아니다.**
레퍼런스 4장 전부가 노랑을 프레임이나 측면 필드로 쓴다. 작은 배지·링크·프로그레스 채움에 쓰인 예가 없다. 넌지시도 그렇게 쓴다. 최소 면적은 **화면 폭의 40% × 높이 88px** 이상이며, 그보다 작으면 시트론을 쓰지 않는다.

**규칙 2 — `alarm`은 액센트가 아니라 경보다.**
`alarm`은 결제 실패·기한 만료·펀딩 미달 **세 상황에서만** 나타난다. 브랜드 색으로 승격시키지 않는다. 크림 배경 + 테라코타 액센트는 흔한 기본값이고, 레퍼런스에도 그 색이 없다.

#### 대비 실측

| 조합 | 비율 | 판정 |
|---|---|---|
| `ink` on `paper` | 13.9:1 | AAA |
| `ink` on `citron` | **11.8:1** | AAA — 시트론 위 텍스트는 항상 `ink` |
| `card` on `green` | 7.6:1 | AAA(대형) / AA(본문) |
| `muted` on `card` | 5.1:1 | AA |
| `muted` on `paper` | **4.6:1** | AA 하한 — 14px 미만 사용 금지 |
| `ink` on `alarm` | 5.1:1 | AA — **경보 위 텍스트는 `ink`** |
| `card` on `citron` | 1.2:1 | **금지** |
| `card` on `alarm` | 2.8:1 | **금지** |

> 흰 텍스트를 시트론이나 경보 위에 올리지 않는다. 둘 다 밝은 색이라 흰색이 사라진다.

### 4.3 타이포그래피

#### 먼저 고칠 것 — 한글 커버리지

현재 `.pen`은 `heading: Newsreader` · `body: Inter` · `caption: Geist Mono`를 쓰고, 25개 텍스트 노드 중 19개가 `$body`다. **세 폰트 모두 한글 글리프가 없다.** Pencil은 이들을 유효한 Google Font로 인정하므로 경고가 뜨지 않고, 한글은 조용히 미지정 폰트로 대체된다. 화면의 거의 모든 글자가 통제 밖에 있다는 뜻이다.

**타입 토큰은 단일 패밀리가 아니라 스택으로 정의한다.**

| 역할 | 라틴·숫자 | 한글 | 비고 |
|---|---|---|---|
| `type-display` | `Newsreader` | `Gowun Batang` | 세리프. 숫자·날짜 중심 |
| `type-text` | `Inter` | **`Pretendard`**(앱) / `Gothic A1`(Pencil) | UI 전반 |
| `type-num` | `Geist Mono` | — | 금액·시각·수량. 한글 없음이 정상 |

> **Pencil은 Pretendard를 렌더할 수 없다.** Google Fonts 목록만 지원하며, 시스템 설치 폰트(`Malgun Gothic`·`Segoe UI`·`Arial` 포함)를 일절 읽지 않는다. `.pen`에서는 `Gothic A1`이 대역이고, 실제 앱은 `next/font/local`로 Pretendard를 쓴다. 이 차이는 의도된 것이며 §13 갭 목록에 남긴다.

#### 세리프는 숫자로 말한다

레퍼런스의 세리프 디스플레이를 그대로 옮기면 한글 본문이 무너진다. 그래서 **세리프의 담당 범위를 좁힌다.**

> `type-display`는 **숫자와 날짜**에 쓴다 — D-day, 금액, 남은 시간, 참여 인원.
> 한글 헤드라인은 **화면당 최대 한 줄**만 `Gowun Batang`으로 두고, 나머지는 전부 `type-text`다.

근거는 제품에 있다. 넌지시에서 감정이 실린 값은 문장이 아니라 숫자다 — 생일까지 남은 3일, 상대가 고른 60,000원, 응답 기한 04:12. 세리프를 그 자리에 두면 장식이 아니라 강조가 된다.

#### 타입 스케일

| 토큰 | 크기 / 행간 | 폰트 | 용도 |
|---|---|---|---|
| `display-xl` | 48 / 1.0 | `type-display` | D-day 숫자(SCR-M3-01) |
| `display-l` | 30 / 1.1 | `type-display` | 금액·펀딩 총액 |
| `headline` | 22 / 1.35 | `type-display`(한글) | 화면당 1줄 |
| `title` | 17 / 1.4, 700 | `type-text` | 섹션·카드 제목 |
| `body` | 14 / 1.6, 400 | `type-text` | 본문 |
| `label` | 12 / 1.4, 600 | `type-text` | 필드 라벨·메타 |
| `micro` | 11 / 1.3, 700 | `type-text` | 배지·탭 라벨 |
| `num-l` | 20 / 1.2 | `type-num` | 카운트다운 |
| `num-s` | 12 / 1.2 | `type-num` | 금액 소계·비율 |

- 한글에는 자간 확장을 넣지 않는다. 라틴 대문자 아이브로우에만 `+0.08em`을 허용한다.
- `micro`를 10px 아래로 내리지 않는다. 현재 `.pen`에 10px 텍스트가 남아 있는데, 11px가 한글 판독 하한이다.

### 4.4 시그니처 — 시트론 필드

화면마다 기억에 남는 요소는 **하나**다.

> **취향 정보를 담은 블록 하나가 시트론 면 위에 놓이고, 그 면은 화면의 한쪽 모서리를 넘어 잘려 나간다.**

```
     화면 경계
     +---------------------------+
     |  [ 흰 카드 ]              |
     |                           |
   __|__________________         |
  |  |                 |         |   <- 시트론 필드가 화면 밖으로 이어짐
  |  |  D-3            |         |      radius 28 · 왼쪽 모서리 잘림
  |  |  서윤이의 생일  |         |
  |__|_________________|         |
     |                           |
     +---------------------------+
```

**왜 잘리는가** — 레퍼런스는 노랑을 *둘러싸는 면*으로 쓴다(예시4는 포스터 전체를 노란 프레임으로 감쌌다). 모바일에는 둘러쌀 여백이 없으므로, **화면 밖으로 이어지는 면**이 그 장치의 정직한 번역이다. 그리고 그것이 이름이기도 하다 — 가운데 놓고 선언하는 대신 비켜서 놓아둔다.

**규율**

| 규칙 | 내용 |
|---|---|
| 수량 | **화면당 하나.** 두 개면 둘 다 죽는다 |
| 대상 | 취향 정보를 나르는 블록에만 — 취향 카드 · D-day · 펀딩 게이지 |
| 방향 | 좌우 중 한쪽만. 같은 화면에서 방향을 바꾸지 않는다 |
| 금지 | 결제·동의·에러·결과 화면에는 **시트론이 없다.** 돈과 실패에 형광 노랑을 올리지 않는다 |
| 텍스트 | 시트론 위 글자는 항상 `ink` |

**적용 화면**

| 화면 | 시트론이 감싸는 것 |
|---|---|
| SCR-M2-04 미리보기 | 대표 태그 2~3개 — 가려진 것 옆의 유일한 색 |
| SCR-M2-06 친구 취향 카드 | 취향 서술 블록 |
| SCR-M1-07 내 취향 | 취향 서술 블록 |
| SCR-M3-01 홈 | D-day 블록 |
| SCR-M4-04 펀딩 상세 | 게이지 + 남은 금액 |

그 외 41개 화면에는 시트론이 없다. **이 색을 아끼는 것이 이 시스템의 유일한 사치다.**

### 4.5 형태 · 간격

| 토큰 | 값 | 적용 |
|---|---|---|
| `radius-field` | 28 | 시트론 필드 · 포레스트 블록 |
| `radius-card` | 20 | 카드 · 시트 |
| `radius-chip` | 12 | 카테고리 칩 · 배지 |
| `radius-pill` | 999 | 버튼 · 탭바 · 필터 |
| `space` | 4의 배수 (4·8·12·16·24·32·40) | 전부 |
| `gutter` | 20 | 화면 좌우 여백 |
| `card-gap` | 12 | 카드 사이 |
| `section-gap` | 32 | 섹션 사이 |

- **그림자를 쓰지 않는다.** 면과 반경으로 층을 만든다. 유일한 예외는 하단 플로팅 네비(`0 4px 24px rgba(24,48,36,.12)`)로, 스크롤되는 내용 위에 떠 있음을 알려야 하기 때문이다.
- 테두리는 `line` 1px. 카드에는 테두리를 쓰지 않고 표면 대비로만 구분한다(`card` on `paper`).

### 4.6 컴포넌트

| 컴포넌트 | 사양 |
|---|---|
| **주 버튼** | `green` 면 · `card` 텍스트 · `radius-pill` · 높이 52 · `title` |
| **보조 버튼** | 투명 · `green` 텍스트 · `line` 1px 테두리 · 높이 48 |
| **위험 버튼** | `alarm` 면 · **`ink` 텍스트** · 실패 복구 화면 전용 |
| **화살표 배지** | 원형 32 · `card` 면 · `green` 화살표. 레퍼런스의 필 버튼 우측 배지 |
| **카드** | `card` 면 · `radius-card` · 패딩 16 |
| **포레스트 블록** | `forest` 면 · `radius-field` · 화면당 최대 1개 |
| **카테고리 칩** | 미선택 `line` 테두리 / 선택 `green` 면 + `card` 텍스트 · `radius-chip` |
| **카운트다운** | `num-l` · 5분 미만 `ink` · 1분 미만 `alarm` |
| **펀딩 게이지** | 트랙 `line` · 채움 `green` · 달성선 위치에 `forest` 1px 눈금 |
| **하단 네비** | `forest` 면 · `radius-pill` · 플로팅 · 활성 탭만 `citron` 아이콘 |

> 하단 네비의 활성 아이콘이 4.4의 "면적" 규칙에 대한 **유일한 예외**다. 탭바는 상시 노출이라 면으로 칠하면 시트론이 흔해진다. 아이콘 하나로 제한한다.

### 4.7 모션

카운트다운이 도는 제품이라 모션이 불안을 만들 수 있다. **적게 쓴다.**

| 대상 | 동작 | 시간 |
|---|---|---|
| 시트론 필드 | 첫 페인트에서 잘린 모서리 쪽으로부터 슬라이드 인 | 180ms `ease-out`, 1회 |
| 펀딩 게이지 | 마운트 시 0 → 현재값 | 400ms `ease-out` |
| 카드 진입 | 없음 | — |
| **카운트다운** | **애니메이션 없음.** 숫자만 바뀐다 | — |
| 결제 처리 | 전용 진행 화면(SCR-M4-06). 스켈레톤 아님 | — |

- `prefers-reduced-motion: reduce`에서 위 전부가 즉시 상태로 바뀐다.
- 카운트다운에 펄스·깜빡임을 넣지 않는다. 5분 기한 자체가 이미 압박이다.

### 4.9 `.pen` 토큰 정리 작업

현재 파일의 중복 토큰을 4.2/4.3에 맞춰 통합해야 한다. 아래는 이 문서가 규정하는 목표 상태다.

| 현재 | 목표 | 처리 |
|---|---|---|
| `bg` `#F4F0E3` / `cream` `#F5F3EE` / `surface` `#F5F3EE` | `paper` `#F5F3EE` | 3개 → 1개 |
| `white` `#FFFFFF` | `card` | 이름만 변경 |
| `green` `#2D5E3A` / `accent` `#2D5E3A` | `green` | 2개 → 1개 |
| `lime` `#F2F15A` | `citron` | 이름 변경 — 역할을 이름에 담는다 |
| `coral` `#F2785C` | `alarm` | 이름 변경 — 경보임을 명시 |
| `font-body` / `body` | `type-text` | 한글 폰트 병기 필요 |
| `font-display` / `heading` | `type-display` | 한글 폰트 병기 필요 |
| `caption` | `type-num` | 역할 명확화 |

## 6. SCR-M1 — 맞춤 취향

> **M1의 설계 원칙**: 대분류는 **잘못된 선물을 걸러내고**, 상세·서술은 **추천의 정확도를 올린다**(PRD). 용도가 다르므로 입력 강제 수준도 다르다. 화면에서는 이것이 **필수 스텝 1개 + 선택 스텝 2개**로 나타난다.

### SCR-M1-01 · 온보딩 인트로

**진입** — SCR-M0-03

```
+----------------------------------+
|                                  |
| 선물이 어긋나는 건               |
| 몰라서입니다.                    |
|                                  |
| 30초면 됩니다.                   |
|                                  |
|  1. 이미 있거나 필요 없는 것     |
|  2. 어느 쪽인지 구분             |
|  3. 좋아하는 것 한 줄  (선택)    |
|                                  |
| 적은 만큼 정확한 선물이          |
| 돌아옵니다.                      |
|                                  |
| [ 시작하기 ]                     |
+----------------------------------+
```

- **근거** — product-lens v3 §1 "점진적 프로필링". 가입 시점에 전부 받으려 하면 이탈한다. **소요 시간을 먼저 알리는 것**이 이 화면의 유일한 일이다.
- **R2 관련** — "적은 만큼 정확한 선물이 돌아옵니다"가 상세 작성을 유도하는 유일한 문구다. 강제하지 않는다는 PRD 정책상 이 문장이 완화책의 전부이므로, 실제 작성률은 마일스톤 1 직후 측정해 검증한다.


| 요소 | 데이터 | 검증 |
|---|---|---|
| 카테고리 | `TasteItem.category_id` | **필수** |
| 종류 | `kind` | **필수** |
| 상세 | `detail` (nullable) | — |
| 메모 | `memo` (nullable) | — |

- **검증 · 예외** — 도메인 모델 §3의 제약 두 가지가 **여기서만** 사용자에게 보인다.

| 위반 | 메시지 |
|---|---|
| `(profile_id, kind, category_id, detail)` 중복 | "이미 같은 항목이 있어요" |
| 같은 카테고리에서 `detail IS NULL`인 `want` ↔ `unwanted` 공존 | "'텀블러'를 원하는 것에 이미 넣어두셨어요. 한쪽만 남겨주세요." |

- **모순 검증은 저장 시점이 아니라 카테고리 선택 직후에 띄운다.** 다 적고 나서 막히면 입력을 통째로 버리게 된다.
- **근거** — 도메인 모델 §3 "제약과 검증". 애플리케이션 레벨 검증이라고 명시된 항목이므로 UI가 그 책임을 진다.

## 7. SCR-M2 — 친구 · 초대 링크

> **M2의 설계 원칙**: 링크를 받으면 **즉시 친구**다(도메인 모델 3-3). 승인 화면이 없다. 통제는 **만료 · revoke · 발급자 알림** 세 가지로 대체되며, 그 셋이 전부 화면을 가진다.

### SCR-M2-01 · 친구 탭

**진입** — 하단 탭 [친구]

```
+----------------------------------+
| 친구                       [ + ] |
|                                  |
| 다가오는 일정                    |
| +------------------------------+ |
| | [o] 김민수   생일     D-3    | |
| | [o] 이서연   기념일   D-12   | |
| +------------------------------+ |
|                                  |
| 친구 5명                         |
|                                  |
| [o] 김민수                     > |
|     커피 · 캠핑 · 러닝           |
| [o] 이서연                     > |
|     향수 · 독서                  |
| [o] 박준호                     > |
|     운동 · 게임                  |
|                                  |
+----------------------------------+
|   홈   | [친구] |  선물  |  마이 |
+----------------------------------+
```

| 요소 | 데이터 | 액션 |
|---|---|---|
| `[ + ]` | — | `>> SCR-M2-02` |
| 다가오는 일정 | `Event` where 친구 소유 · 날짜 임박순 | 탭 → SCR-M2-06 |
| 친구 목록 | `Friendship` where `status='active'` | 탭 → SCR-M2-06 |
| 대표 태그 | `TasteItem` where `kind='want'` 의 `Category.name` 최신 3건 | — |

- **상태 · 예외**
  - 친구 0명: "링크 하나면 시작됩니다" + `[ 친구에게 링크 보내기 ]` (SCR-C-01)
  - 다가오는 일정 0건: 섹션 자체를 숨긴다. 빈 카드를 두지 않는다.
  - 친구가 `want` 항목이 없으면 대표 태그 자리를 비운다. 대체 문구를 넣지 않는다 — 상대의 미입력을 노출하는 꼴이 된다.
- **접근 제어** — 목록은 `status='active'`만. `removed`는 조회되지 않는다.
- **근거** — PRD "친구 | 친구 목록 · 취향 카드 · 취향에 맞는 선물 추천". 캘린더 탭이 여기로 흡수됐다(product-lens v3 §5-④).
- **갭** — 대표 태그 선정 규칙이 "최신순 3건으로 충분한가"로 열려 있다(도메인 모델 §13-5). 화면은 최신순을 전제한다.

### SCR-M2-02 · 친구 추가 링크 발급 · 공유

**진입** — SCR-M2-01의 `[ + ]` / SCR-M1-05

```
+----------------------------------+
| <  친구 추가                     |
|                                  |
| 링크를 보내면                    |
| 받은 사람이 바로 친구가 됩니다.  |
|                                  |
| +------------------------------+ |
| | neonjisi.app/i/x7Kq2mA9...   | |
| +------------------------------+ |
|             ( 복사 )             |
|                                  |
| 7일 후 만료                      |
| 여러 명에게 보낼 수 있어요       |
|                                  |
| [ 공유하기 ]                     |
|                                  |
| ( 링크 관리 )                    |
|                                  |
+----------------------------------+
```

| 요소 | 데이터 | 액션 |
|---|---|---|
| 링크 | `FriendInviteLink.token` (32바이트 URL-safe) | 복사 |
| 만료 안내 | `expires_at` = 발급 + `FRIEND_INVITE_TTL`(7일) | — |
| 공유하기 | — | OS 공유 시트 |
| 링크 관리 | — | `>> SCR-M2-03` |

- **핵심 문구** — "받은 사람이 **바로** 친구가 됩니다"를 발급 시점에 명시한다. 승인 단계가 없다는 사실을 발급자가 링크를 뿌리기 **전에** 알아야 한다. 이것이 3-3에서 승인을 없앤 대가로 지불하는 고지다.
- **상태 · 예외** — 활성 링크가 이미 있으면 새로 발급하지 않고 기존 링크를 보여준다. 다회용이므로 매번 발급할 이유가 없다.
- **근거** — 도메인 모델 §4 `FriendInviteLink`. 다회용 · 만료 · revoke.

### SCR-M2-03 · 내 초대 링크 관리

**진입** — SCR-M2-02 / SCR-M1-06

```
+----------------------------------+
| <  초대 링크                     |
|                                  |
| 사용 중                          |
| +------------------------------+ |
| | neonjisi.app/i/x7Kq2mA9...   | |
| | 3명 사용 · 5일 후 만료       | |
| |          ( 복사 ) ( 중지 )   | |
| +------------------------------+ |
|                                  |
| 지난 링크                        |
```

| 요소 | 데이터 | 액션 |
|---|---|---|
| 사용 횟수 | `used_count` | — |

- **근거** — 도메인 모델 §4, 3-3.

### SCR-M2-04 · 초대 링크 랜딩 — 미리보기 (비가입)

**진입** — 외부 링크 `/i/{token}`. **앱 셸 밖. 로그인 불필요.**

```
+----------------------------------+
|                                  |
|                                  |
|          +---------+             |
|          |   [o]   |             |
|          +---------+             |
|                                  |
|            김지은                |
|                                  |
|       커피 · 캠핑 · 러닝         |
|                                  |
|                                  |
| 김지은님이 받고 싶은 선물을      |
| 넌지시 남겨두었습니다.           |
|                                  |
| 친구가 되면 볼 수 있어요         |
|   원하는 것                      |
|   이미 있는 것 / 관심 없는 것    |
|   취향 서술                      |
|                                  |
| [ 넌지시 시작하기 ]              |
|                                  |
+----------------------------------+
```

| 요소 | 데이터 | 노출 |
|---|---|---|
| 표시명 | `User.display_name` | **공개** |
| 프로필 이미지 | `User.avatar_url` | **공개** |
| 대표 태그 2~3개 | `TasteItem(kind='want').Category.name` 최신순 | **공개** |
| 그 외 취향 전체 | `TasteItem` · `TasteProfile.description` | **비공개** |

- **접근 제어** — 도메인 모델 §7:
  ```
  canViewPreview(token) := 유효한 FriendInviteLink (미만료 · 미revoke)
  ```
- **상태 · 예외**

| 상황 | 화면 |
|---|---|
| 만료된 토큰 | "링크가 만료됐어요. 보낸 분께 다시 요청해주세요." — 표시명도 노출하지 않는다 |
| 중지된 토큰 | 위와 동일 문구. 만료/중지를 구분해 알리지 않는다 |
| 없는 토큰 | 위와 동일 문구 |
| **이미 로그인 + 이미 친구** | 미리보기 대신 `>> SCR-M2-06`(친구 상세) 직행 |
| 이미 로그인 + 아직 친구 아님 | 미리보기를 건너뛰고 `>> SCR-M2-05` 즉시 성사 |
| **자기 자신의 링크** | "본인 링크입니다" — 친구 성사시키지 않는다 (`giver <> receiver` 원칙) |

- **근거** — PRD R1의 완화책 전문: "링크 열람 시 **미리보기**(이름 + 대표 태그 2~3개)까지는 비가입 노출, 상세는 친구 수락 후."
- **설계 판단 — "친구가 되면 볼 수 있어요" 목록이 이 화면의 전환 장치다.** 대표 태그만으로는 가입할 이유가 약하다. **가려진 것이 무엇인지 이름으로 보여주는 것**이 가입 동기를 만든다. 값을 보여주지 않으면서 항목명은 보여준다.
- **프라이버시 경계** — 만료·중지·부재를 하나의 문구로 합친 것은 의도적이다. 토큰 유효성 판정 결과를 세분화하면 토큰 탐색에 힌트를 준다.

### SCR-M2-05 · 초대 수락 완료

**진입** — SCR-M2-04 → 가입 → 온보딩 완료 후 자동 / 로그인 상태에서 유효 토큰 열람 시 즉시

```
+----------------------------------+

|                                  |

|      친구가 되었습니다           |
```

- **근거** — 도메인 모델 3-3 "링크를 받으면 즉시 친구", §4 `friendship_pair_active` partial index.

- **진행 중의 정의**(도메인 모델 §7)
  - `GiftRequest.status ∈ { pending, paying, payment_failed }`
  - `Funding.status ∈ { open, succeeded }`
- **해제 후에도 열리는 것** — 표시명 · 프로필 이미지 · 해당 거래의 선물 항목 · 금액 · (수령자가 그 거래에 제공한) 배송지. **전부 거래 엔티티가 자기 안에 복사해 둔 스냅샷이다.** 따라서 화면은 `Friendship`을 조회하지 않고 `GiftRequest` / `Funding`만 읽으면 된다.
- **닫히는 것** — 취향 항목 전체 · 취향 서술 · 다른 친구 목록 · 다른 거래 이력.
- **근거** — PRD D3, 도메인 모델 §7. 두 번째 안내 문구("진행 중인 선물·펀딩은 그대로 진행됩니다")가 D3 예외를 사용자에게 고지하는 유일한 지점이다.

## 8. SCR-M3 — 선물

> **M3의 설계 원칙 3가지**
> 1. **거절 버튼이 없다.** `declined` 상태가 없으므로(도메인 모델 §5) 화면에도 만들 수 없다. 수령자의 선택지는 승인 / 대안 제시 / 무응답뿐이다.
> 2. **결제수단이 요청보다 앞선다.** 빌링키 없이는 요청을 만들 수 없다.
> 3. **동의는 요청마다, 결제수단은 재사용.** 동의 화면은 매번 뜨고, 카드 등록은 한 번만 한다.

### SCR-M3-01 · 홈 탭

**진입** — 하단 탭 [홈] · 로그인 후 기본 화면

```
+----------------------------------+
| 넌지시                    (알림3)|
|                                  |
| 응답 기다리는 중                 |
| +------------------------------+ |
| | [o] 김민수님이 보낸 선물     | |
| | 핸드드립 케틀 · 89,000원     | |
| | 남은 시간  04 : 12           | |
| |        [ 확인하기 ]          | |
| +------------------------------+ |
|                                  |
| 다가오는 일정                    |
| +------------------------------+ |
| | [o] 김민수  생일     D-3   > | |
| | [o] 이서연  기념일   D-12  > | |
| +------------------------------+ |
|                                  |
| 진행 중 펀딩                     |
| +------------------------------+ |
| | 이서연님 생일 · 다이슨       | |
| | ====================----     | |
| | 320,000 / 400,000  D-5     > | |
| +------------------------------+ |
|                                  |
+----------------------------------+

+----------------------------------+
```

| 섹션 | 데이터 | 정렬 · 조건 |
|---|---|---|
| 응답 기다리는 중 | `GiftRequest` where `receiver_id = me AND status='pending'` | `respond_due_at` 임박순 |
| 다가오는 일정 | `Event` where 친구 소유 · `is_recurring` 반영 | 날짜 임박순 |
| 진행 중 펀딩 | `Funding` where `status='open'` AND (내가 organizer / contributor / receiver) | `deadline` 임박순 |
| 알림 배지 | `Notification` where `read_at IS NULL` | `>> SCR-M3-02` |

- **핵심 — 승인 대기가 최상단이다.** `GIFT_RESPOND_TTL`이 5분(시연 기준)이므로 스크롤 아래에 두면 만료된다. product-lens v3 §5-②가 지적한 "승인/반려 진입점이 네비에 없다"의 해소 지점이다.
- **카운트다운** — `respond_due_at`(생성 시 절대 시각으로 스냅샷)과 현재 시각의 차. 0이 되면 카드를 만료 상태로 바꾼다.
- **상태 · 예외**
  - 세 섹션 모두 비면 SCR-C-01의 홈 빈 상태. 친구가 0명이면 "친구를 추가하면 여기에 일정이 모입니다" + 링크 발급 유도.
  - 승인 대기 0건이면 섹션 자체를 숨긴다.
  - 만료가 임박한 요청(1분 미만)은 시간 표시를 강조한다.
- **만료 판정** — 조회 시점의 지연 평가(도메인 모델 §8). 이 화면을 여는 것이 곧 만료 판정 트리거다. 배치가 없으므로 오차도 없다.
- **근거** — PRD "홈 | 다가오는 일정 · 승인 대기 · 진행 중 펀딩". product-lens v3 §5-① "홈은 관계 중심 액션 허브여야 합니다."

### SCR-M3-03 · 선물 탭 — 검색 · 카테고리

**진입** — 하단 탭 [선물]

```
+----------------------------------+
| 선물                             |
| +------------------------------+ |
| | 검색                         | |
| +------------------------------+ |
|                                  |
| 누구에게 줄까요?                 |
| ( 전체 ) ([o]민수) ([o]서연)     |
|                                  |
| 카테고리                         |
| +--------+ +--------+ +--------+ |
| | 텀블러 | |  향수  | |  양말  | |
| +--------+ +--------+ +--------+ |
| +--------+ +--------+ +--------+ |
| | 머그컵 | | 다이어리| | 키링  | |
| +--------+ +--------+ +--------+ |
|                                  |
| 인기 선물                        |
| +------------+ +------------+    |
| |    [o]     | |    [o]     |    |

```

| 요소 | 데이터 | 액션 |
|---|---|---|
| 검색 | `Product.name` | 결과 목록 |
| 대상 필터 | `Friendship` where `active` | 선택 시 해당 친구의 `unwanted` 카테고리 제외 |
| 카테고리 | `Category` (취향과 **같은 마스터**) | 목록 필터 |
| 상품 카드 | `Product` where `is_active` | `>> SCR-M3-04` |

- **핵심 — 대상 필터가 이 탭을 쇼핑앱과 구분한다.** 친구를 고르면 그 친구가 `unwanted`로 표시한 카테고리의 상품이 목록에서 빠진다. `TasteItem.category_id`와 `Product.category_id`가 같은 마스터를 가리키므로 조인 한 번으로 처리된다(도메인 모델 §2 · §5).
- **`have`는 제외하지 않고 표시만 바꾼다.** "이미 갖고 있어요"와 "관심 없어요"는 다르다 — 같은 텀블러라도 다른 브랜드는 성립할 수 있다. 목록에서 지우는 것은 `unwanted`뿐이다.
- **상태 · 예외** — 대상 필터를 걸었는데 결과가 0건이면 "민수님이 관심 없다고 한 것들을 빼니 남는 게 없어요. 전체에서 골라보세요."
- **근거** — PRD "선물 | 검색 · 카테고리".
- **R7 관련** — PRD가 "친구 탭에 취향 기반 추천이 들어가면서 자유 검색 탭의 진입 동기가 약해진다"고 본 리스크다. **대상 필터를 이 탭에 넣은 것이 완화책이다.** 마일스톤 3 이후 탭 진입률을 측정해 흡수 여부를 판단한다.

### SCR-M3-04 · 상품 상세

**진입** — SCR-M3-03 / SCR-M3-05

```
+----------------------------------+
| <                                |
| +------------------------------+ |
| |                              | |
| |            [o]               | |
| |                              | |
| +------------------------------+ |
|                                  |
| 핸드드립 케틀                    |
| 89,000원                         |
| 카테고리 · 커피용품              |
|                                  |
| +------------------------------+ |
| | [o] 민수님이 원하는 것에     | |
| |     적어둔 항목입니다        | |
| +------------------------------+ |
|                                  |
|                                  |
| [ 선물하기 ]                     |
| ( 여럿이 모아서 선물하기 )       |
+----------------------------------+
```

| 요소 | 데이터 | 액션 |
|---|---|---|
| 이미지 · 이름 · 가격 | `Product` | — |
| 카테고리 | `Product.category_id → Category.name` | — |
| 취향 매칭 배너 | `TasteItem` 대조 결과 | — |
| 선물하기 | — | `>> SCR-M3-08` |
| 모아서 선물 | — | `>> SCR-M4-01` (M4) |

- **취향 매칭 배너의 3가지 상태** — 대상 친구가 선택된 상태에서만 뜬다.

| 조건 | 배너 |
|---|---|
| 그 친구의 `want`와 카테고리·상세 일치 | "민수님이 원하는 것에 적어둔 항목입니다" (긍정) |
| `have`와 카테고리 일치 | "민수님이 이미 갖고 있다고 한 종류예요" (주의) |
| `unwanted`와 카테고리 일치 | **`[ 선물하기 ]` 비활성** + "민수님이 관심 없다고 한 종류예요" |

- **`unwanted` 상품에 대해 선물하기를 막는 것이 이 제품의 핵심 가치가 화면에 드러나는 지점이다.** 검색으로 우회해 들어올 수 있으므로 목록 필터만으로는 부족하다.
- **상태 · 예외** — 대상 친구 미선택 시 배너 없음. `is_active = false`인 상품은 진입 자체를 막는다.
- **근거** — 도메인 모델 §5 `Product`: "`category_id`가 `TasteItem`과 같은 마스터를 가리키므로 수령자가 `unwanted`로 표시한 카테고리의 상품을 조인 한 번으로 걸러낼 수 있다."

### SCR-M3-05 · 친구 맞춤 추천

**진입** — SCR-M2-06의 `[ 이 취향에 맞는 선물 보기 ]`

```
+----------------------------------+
| <  민수님에게 어울리는 선물      |
|                                  |
| 원하는 것에 적어둔 것            |
| +------------+ +------------+    |
| |    [o]     | |    [o]     |    |
| | 핸드드립   | | 원두구독   |    |
| | 89,000원   | | 60,000원   |    |
| +------------+ +------------+    |
|                                  |
| 취향에 맞을 것 같은 것           |
| +------------+ +------------+    |
| |    [o]     | |    [o]     |    |
| | 온도계케틀 | | 드립스탠드 |    |
| | 45,000원   | | 32,000원   |    |
| +------------+ +------------+    |
|                                  |
| +------------------------------+ |
| | 텀블러 · 지갑은 빼고         | |
| | 보여드리고 있어요            | |
| +------------------------------+ |
|                                  |
+----------------------------------+
```

| 섹션 | 데이터 | 근거 |
|---|---|---|
| 원하는 것에 적어둔 것 | `TasteItem(kind='want')` → `Product` 매칭 | 확실한 신호 |
| 취향에 맞을 것 같은 것 | `want`의 `Category` 기준 동일 카테고리 상품 | 카테고리 확장 |
| 제외 안내 | `TasteItem(kind='unwanted').Category.name` | 왜 안 보이는지 설명 |

- **"제외 안내"가 이 화면의 신뢰 장치다.** 필터가 조용히 동작하면 사용자는 목록이 빈약하다고 느낀다. **무엇을 걸러냈는지 밝히는 것**이 필터를 기능으로 인식시킨다.
- **상태 · 예외**
  - 상대가 `want`를 하나도 안 적었으면 첫 섹션이 통째로 빈다. 그 경우 "민수님이 아직 원하는 걸 적지 않았어요. 관심 없다고 한 것만 빼고 보여드릴게요." → 전체 카탈로그를 `unwanted` 제외로 보여준다.
  - 매칭 결과 0건이면 SCR-M3-03(전체 선물 탭)으로 유도한다.
- **접근 제어** — `canViewTasteProfile`이 참일 때만 진입 가능. 관계 해제 시 이 화면은 닫힌다(취향 상세를 쓰기 때문이다).
- **근거** — PRD "친구 | 취향에 맞는 선물 추천".
- **갭** — "취향에 맞을 것 같은 것"의 랭킹 규칙은 정의되지 않았다. 카테고리 일치 외의 신호(`description` 텍스트 분석 등)는 도메인 모델에 없다. §13에 올린다.

### SCR-M3-06 · 결제수단 등록

**진입** — SCR-M3-08에서 활성 결제수단이 없을 때 강제 진입 / SCR-M3-07

```
+----------------------------------+

|                                  |
| +------------------------------+ |
| |                              | |
| |   (포트원 카드 등록 화면)     ||
| |                              | |
| |                              | |
| +------------------------------+ |
|                                  |
| 카드 정보는 넌지시에 저장되지    |
| 않습니다. 결제사가 보관합니다.   |
|                                  |
```

| 요소 | 데이터 | 비고 |
|---|---|---|
| 카드 등록 위젯 | PortOne SDK | 카드번호·CVC는 **앱이 만지지 않는다** |
| 저장 결과 | `PaymentMethod.billing_key` (**암호화**) | |

- **동작** — 성공 시 `PaymentMethod` 생성(`status='active'`) 후 직전 화면으로 복귀. SCR-M3-08에서 강제 진입한 경우 요청 플로우가 이어진다.
- **핵심 — 빌링키는 사용자당 재사용한다.** 요청마다 새로 발급하면 카드 등록을 매번 시키는 꼴이 된다(도메인 모델 §5). 그래서 이 화면은 **최초 1회만** 뜬다.
- **상태 · 예외** — 등록 실패 시 재시도. `status='expired'`인 기존 수단이 있으면 교체 등록으로 동작한다.
- **근거** — 도메인 모델 §5 `PaymentMethod`, `GiftRequest` 제약: "요청 생성 시 giver에게 `status='active'`인 `PaymentMethod`가 있어야 한다. **빌링키 등록이 요청보다 앞선다**."
- **갭** — PortOne 연동 상세(호출 시퀀스·웹훅·테스트 모드)는 M3 착수 시점에 정한다(도메인 모델 §12).

- **상태 · 예외**

### SCR-M3-11 · 요청 상세 (주는 사람)

**진입** — SCR-M3-10 / SCR-M3-18 / `gift_countered` 알림

```
+----------------------------------+
| <  보낸 선물                     |
|                                  |
| [o] 김민수                       |
|                                  |
| 상태  응답 기다리는 중           |
| 남은 시간  03 : 21               |
|                                  |
| +------------------------------+ |
| | [o] 핸드드립 케틀            | |
| |     89,000원                 | |
| +------------------------------+ |
|                                  |
| 보낸 시각  2026-08-26 14:02      |
| 결제수단   신한 **** 4821        |
|                                  |
|                                  |
| ( 요청 취소 )                    |
+----------------------------------+
```

**상태별 화면 변형**

| `status` | 상단 표시 | 하단 액션 |
|---|---|---|
| `pending` | "응답 기다리는 중" + 카운트다운 | `( 요청 취소 )` |
| `paying` | "결제 중" | 없음 |
| `paid` + `resolution='approved'` | "결제 완료" | `( 내역 보기 )` |
| `paid` + `resolution='countered'` | **"민수님이 다른 상품을 골랐어요"** + 원래 상품 → 최종 상품 대조 | `( 내역 보기 )` |

| `expired` | "응답 기한이 지났어요" | `[ 다시 보내기 ]` |
| `cancelled` | "취소됨" | 없음 |

**대안 제시된 경우의 표시**

```
| 민수님이 다른 상품을 골랐어요    |
|                                  |
| +------------------------------+ |
| | 요청한 것                    | |
| | [o] 핸드드립 케틀  89,000원  | |
| +------------------------------+ |
|              |                   |
|              v                   |
| +------------------------------+ |
| | 결제된 것                    | |
| | [o] 원두 정기구독  60,000원  | |
| +------------------------------+ |
|                                  |
| 차액 29,000원은 청구되지         |
| 않았습니다.                      |
```

- **문구 원칙** — "반려"·"거절"을 쓰지 않는다. "다른 상품을 골랐어요"가 사실 서술이면서 감정 비용이 가장 낮다. **차액 미청구를 함께 밝히는 것**이 R6 완화의 절반이다 — 손해가 없다는 사실이 감정을 눌러준다.
- **취소 가능 구간** — `pending`에서만. `paying` 진입 후에는 불가(PG 호출이 이미 나갔다).
- **관계 해제 시** — 이 화면은 `GiftRequest`의 스냅샷 필드(`receiver_display_name` · `product_snapshot`)만 읽으므로 **계속 열린다**(D3 예외). 단 `[o]` 아바타 옆에서 친구 상세로 들어가는 링크는 막힌다.
- **근거** — PRD "대안 제시 사실 고지 | **주는 사람에게 알린다**", R6. 도메인 모델 §5 `resolution` 필드.

| 액션 | 결과 | `resolution` |
|---|---|---|

| 상황 | 처리 |
|---|---|

| 응답 중 만료 | 액션 실패. 만료 안내로 전환 |

### SCR-M3-14 · 배송지 입력

**진입** — SCR-M3-12의 승인 / SCR-M3-13의 확정. **양쪽 경로가 여기서 합류한다.**

```
+----------------------------------+

| ________________________________ |
|                                  |
| 주소                             |
| ________________________________ |
```

| 요소 | 데이터 | 비고 |
|---|---|---|
| 배송지 전체 | `GiftRequest.shipping_address_snapshot` (jsonb) | **이 거래에만** |

- **핵심 — 프로필의 기본 배송지가 아니다.** 도메인 모델 §7: "수령자가 **그 거래에** 제공한 것만. 프로필의 기본 배송지가 아니다." 관계가 해제돼도 이 주소는 해당 거래에서 계속 보이므로, 거래 단위로 제공하는 구조여야 프라이버시가 성립한다.

- **완료 시 동작** — `pending → paying` 조건부 UPDATE로 잠근 뒤 PG 호출. 그 UPDATE가 0행이면 이미 진행 중이므로 중단한다(도메인 모델 §5: "`paying`은 멱등성 장치다"). 화면에서는 이 구간에 로딩을 걸고 버튼을 비활성화한다.
- **상태 · 예외** — 결제 처리 중 이탈해도 결과는 알림으로 전달된다. 이 화면에 사용자를 붙잡아 둘 필요가 없다.
- **갭** — 재사용 가능한 기본 배송지는 도메인 모델에 없다. 거래마다 재입력하는 마찰이 있으나, 이는 D3의 프라이버시 설계를 지키기 위한 의도된 비용이다. §13 참조.

## 9. SCR-M4 — 펀딩

> **M4의 설계 원칙 3가지**
> 1. **개설자 = 수령자면 차액 개념이 사라진다.** `min_amount = goal_amount`가 강제되므로(도메인 모델 5-5) 개설 플로우가 한 스텝 짧아진다. R3가 화면 레벨에서 해소된다.
> 2. **참여는 선결제다.** 예약(`reserved`) → 결제(`paid`) 2단계이며, 예약 시점에 잔여 금액이 잠긴다.
> 3. **잔여 금액을 항상 보여준다.** R4(첫 참여자가 전액을 채우는 문제)의 유일한 완화책이 화면 표시다.

### SCR-M4-02 · 펀딩 개설 2/3 — 목표 · 달성선 · 마감

**주최자 ≠ 수령자 (친구에게)**

| 요소 | 데이터 | 제약 |
|---|---|---|
| 목표 금액 | `goal_amount` | |
| 최소 달성선 | `min_amount` | **CHECK `min_amount <= goal_amount`** |
| 마감일 | `deadline` | 미래 시각 |

- **개설자 = 수령자일 때 `min_amount` 입력을 잠그고 `goal_amount`를 그대로 표시한다.** 값을 숨기지 않고 잠그는 이유는, 왜 그런지를 바로 아래 문구가 설명하기 때문이다. 필드를 숨기면 규칙이 보이지 않는다.
- **이 화면이 R3를 해소한다.** PRD R3("개설자=수령자이면 자기 선물의 차액을 자기가 내는 구조")는 차액이 존재할 수 없게 만들어 사라진다. 3스텝이 2스텝이 되는 것도 같은 이유다.
- **상태 · 예외**

| 위반 | 메시지 |
|---|---|
| `min_amount > goal_amount` | "최소 달성선은 목표 금액보다 클 수 없어요" |
| `deadline <= now()` | "마감일은 오늘 이후로 정해주세요" |
| `goal_amount < 상품 가격` | 경고만. 상품 가격과 목표를 다르게 잡는 것 자체는 막지 않는다 |

- **근거** — PRD 펀딩 정책 표 전체. 도메인 모델 §6 `Funding`.

### SCR-M4-04 · 펀딩 상세

**진입** — SCR-M3-01 / SCR-M4-08 / 공유 링크

```
|                                  |

| ========================----     |

|                                  |
| 남은 금액   80,000원             |
| 마감까지    D-5                  |
|                                  |
| 참여자 4명                       |
| +------------------------------+ |
| | [o] 김민수     100,000원     | |
| | [o] 박준호      80,000원     | |

| | [o] 나           60,000원    | |
| +------------------------------+ |
```

| 요소 | 데이터 | 계산 |
|---|---|---|
| 모인 금액 | `FundingContribution` where `status='paid'` 합 | **판정용 총액** |
| 남은 금액 | `goal_amount - (reserved + paid 합)` | **캡 계산용 총액** |
| 달성선 표시 | `min_amount` 도달 여부 | |
| 참여자 목록 | 아래 접근 제어 참조 | |

- **총액의 정의가 두 곳에서 다르다**(도메인 모델 §6). 화면도 그것을 반영한다.

| 표시 | 합산 대상 | 이유 |
|---|---|---|
| "320,000 / 400,000원" · 달성선 판정 | `paid`만 | 결제되지 않을 수도 있는 돈으로 성사를 선언하지 않는다 |
| "남은 금액 80,000원" | `reserved` + `paid` | 동시 참여가 목표를 넘지 않게 한다 |

  두 숫자가 어긋나 보일 수 있다(모인 320,000 + 남은 80,000 = 400,000이지만 진행바는 320,000까지). 예약 중인 금액이 있으면 "결제 중 20,000원"을 별도 줄로 표기해 해소한다.

- **접근 제어 — 지분 공개**(도메인 모델 §6, PRD R5)

```
canViewAllContributions(viewer, funding) := viewer 는 organizer 또는 receiver
canViewOwnContribution(viewer, funding)  := viewer 는 contributor
```

| 보는 사람 | 참여자 목록 |
|---|---|
| 주최자 · 수령자 | **전원 이름 + 금액** |
| 일반 참여자 | 이름만 나열 + **자기 금액만** 숫자 표시 |
| 비참여 친구 | 이름만 나열, 금액 전부 숨김 |

- **상태별 화면 변형**

| `status` | 상단 | 하단 액션 |
|---|---|---|
| `open` | 진행바 + 남은 금액 + D-day | `[ 참여하기 ]` |
| `open` + 잔액 0 | "목표를 채웠어요" | 참여 버튼 비활성 |
| `succeeded` | "성사되었습니다" | `( 결과 보기 )` |
| `settled` | "선물이 확정되었어요" | `( 결과 보기 )` |
| `failed` | "달성선에 못 미쳐 취소됐어요" | `( 환불 내역 )` |
| `cancelled` | "주최자가 취소했어요" | `( 환불 내역 )` |
| 이미 참여함 | 참여 금액 표시 | `( 참여 취소 )` — **`reserved` 상태에서만** |

- **R4 완화** — PRD: "**잔여 금액 실시간 표시**와 참여 전 확인 단계로 완화." 남은 금액이 이 화면 상단에 고정되는 것이 그 절반이고, 나머지 절반은 SCR-M4-05다.
- **`(:)` 메뉴** — 주최자에게만 `펀딩 취소`. 취소 시 전 참여 건 환불(도메인 모델 §6).
- **관계 해제 시** — `receiver_display_name` · `product_snapshot`만으로 렌더되므로 진행 중(`open` / `succeeded`)이면 계속 열린다(D3 예외).

### SCR-M4-05 · 펀딩 참여 — 금액 입력

**진입** — SCR-M4-04의 `[ 참여하기 ]`

```
+----------------------------------+
| <  참여하기                      |
|                                  |
| 얼마나 보태시겠어요?             |
|                                  |
| ________________________ 원      |
|                                  |
| ( 2만원 ) ( 5만원 ) ( 8만원 전액)|
|                                  |
| 남은 금액  80,000원              |
|                                  |
| +------------------------------+ |
| | 참여 금액은 서연님과         | |
| | 주최자에게 공개됩니다.       | |
| +------------------------------+ |
|                                  |
| +------------------------------+ |
| | 달성선에 못 미치면 전액      | |
| | 환불됩니다.                  | |
| +------------------------------+ |
|                                  |
| 결제수단 신한 **** 4821  ( 변경 )|
| [ 결제하고 참여하기 ]            |
+----------------------------------+
```

| 요소 | 데이터 | 제약 |
|---|---|---|
| 금액 | `FundingContribution.amount` | **1인 상한 없음** · 잔여 금액 이하 |
| 빠른 선택 | 잔여 금액 기준 | 마지막 칩은 항상 "전액" |
| 결제수단 | `PaymentMethod` | `active` 필수 |

- **두 개의 고지가 나란히 있는 것이 이 화면의 요구사항이다.**

| 고지 | 근거 |
|---|---|
| "참여 금액은 서연님과 주최자에게 공개됩니다" | PRD R5 — "참여 시점에 '수령자에게 금액이 공개됩니다' 명시" |
| "달성선에 못 미치면 전액 환불됩니다" | 선결제 구조(5-1)이므로 돈이 먼저 나간다는 사실을 알려야 한다 |

- **R4 관련** — 1인 최대 참여액에 제한이 없으므로(PRD) 첫 참여자가 "전액" 칩을 눌러 펀딩을 끝낼 수 있다. **화면은 그것을 막지 않는다** — 정책이 허용한다. 잔여 금액 표시와 확인 단계가 완화책의 전부이며, 재발 시 정책 재검토가 PRD의 입장이다.
- **상태 · 예외**

| 상황 | 처리 |
|---|---|
| 입력 > 잔여 금액 | "남은 금액은 80,000원이에요" — 버튼 비활성 |
| 진입 중 잔액 소진 | "방금 목표를 채웠어요" → SCR-M4-04 복귀 |
| 이미 참여함 | 추가 참여 허용 (별도 `FundingContribution` 행) |

| 단계 | 서버 | 화면 |
|---|---|---|

## 10. SCR-C — 공통 상태 · 패턴

### SCR-C-01 · 빈 상태

빈 상태는 **다음 행동을 지시하는 자리**다. "없습니다"로 끝내지 않는다.

| 화면 | 조건 | 문구 | 액션 |
|---|---|---|---|
| SCR-M3-01 홈 | 친구 0명 | "친구를 추가하면 여기에 일정이 모입니다" | `[ 친구에게 링크 보내기 ]` |
| SCR-M3-01 홈 | 친구는 있고 일정·요청 0 | "지금은 조용하네요" | `( 친구 취향 둘러보기 )` |
| SCR-M2-01 친구 | 친구 0명 | "링크 하나면 시작됩니다" | `[ 친구에게 링크 보내기 ]` |
| SCR-M1-07 내 취향 | `want` 0건 | "친구가 볼 수 있게 원하는 걸 적어보세요" | `[ + 추가 ]` |
| SCR-M1-07 내 취향 | `description` 없음 | "왜 좋아하는지 한 줄이면 선물이 훨씬 정확해집니다" | `[ 적어보기 ]` |
| SCR-M2-06 친구 상세 | 상대의 `want`·`description` 비어 있음 | "아직 적은 게 많지 않아요" | 선물 보기는 유지 |
| SCR-M3-18 선물 내역 | 0건 | "아직 주고받은 선물이 없어요" | `( 친구 보러 가기 )` |
| SCR-M4-08 펀딩 내역 | 0건 | "아직 참여한 펀딩이 없어요" | 없음 |
| SCR-M3-07 결제수단 | 0건 | "선물을 보내려면 결제수단이 필요합니다" | `[ 등록하기 ]` |

- **SCR-M1-07의 두 빈 상태가 R2 완화의 실제 지점이다.** 온보딩에서 skip한 사용자를 되돌리는 유일한 화면이므로, 여기 문구를 약하게 쓰면 상세 작성률이 오르지 않는다.

### SCR-C-02 · 에러

Next.js App Router의 `error.tsx` 경계를 사용한다(CLAUDE.md).

```
+----------------------------------+
|                                  |
|              (!)                 |
|                                  |
|   문제가 생겼어요                |
|                                  |
| 잠시 후 다시 시도해주세요.       |
|                                  |
| [ 다시 시도 ]                    |
| ( 홈으로 )                       |
|                                  |
+----------------------------------+
```

| 상황 | 처리 |
|---|---|
| 네트워크 실패 | 위 화면 + 재시도 |
| 권한 없음 (관계 해제 등) | "볼 수 없는 화면이에요" + 홈으로 |
| 없는 리소스 | `not-found.tsx` |
| 결제 오류 | **이 화면을 쓰지 않는다.** SCR-M3-16 / SCR-M4-06의 전용 화면으로 보낸다 |

- **결제 실패를 일반 에러로 처리하지 않는 것이 원칙이다.** 돈이 오간 실패는 다음 행동(재시도·결제수단 변경)이 정해져 있으므로 전용 화면이 필요하다.
- **에러 메시지에 내부 정보를 담지 않는다** — 스택, 쿼리, 엔티티 id 노출 금지.

### SCR-C-04 · 확인 다이얼로그

되돌릴 수 없는 동작에만 쓴다. 남용하면 사용자가 읽지 않고 누른다.

```
+----------------------------------+

|                                  |

+----------------------------------+
```

**사용처**

| 화면 | 동작 | 되돌릴 수 있나 |
|---|---|---|
| SCR-M1-07 | 취향 항목 삭제 | ❌ hard delete |
| SCR-M2-03 | 초대 링크 중지 | ❌ `revoked_at` |

| SCR-M3-11 | 요청 취소 | ❌ |
| SCR-M4-04 | 펀딩 취소 (주최자) | ❌ 전 참여 건 환불 |
| SCR-M3-07 | 결제수단 삭제 | ⚠️ 진행 중 요청에 영향 |

**쓰지 않는 곳** — 선물 승인(SCR-M3-12)과 펀딩 참여(SCR-M4-05)는 화면 자체가 확인 단계이므로 다이얼로그를 겹치지 않는다.

| `Event` | SCR-M3-17 | SCR-M3-01 · SCR-M2-01 · SCR-M2-06 |
| `Funding` | SCR-M4-03(생성) · SCR-M4-04(취소) | SCR-M4-04 · SCR-M4-07 · SCR-M4-08 · SCR-M3-01 |
| `FundingContribution` | SCR-M4-05 → SCR-M4-06 | SCR-M4-04 · SCR-M4-08 |

### 확인된 것

- **쓰기 화면 없는 엔티티 0건.** 모든 엔티티에 데이터가 들어오는 경로가 있다.
- **읽기 화면 없는 엔티티 0건.** 저장만 하고 안 보여주는 데이터가 없다.
- `Category`와 `Product`는 시드 데이터이므로 앱 내 생성 화면이 없다. 관리자 도구는 MVP 범위 밖이다.
- `Payment`와 `Notification`은 서버가 상태 전이 시 생성한다. 사용자가 직접 만드는 화면이 없는 것이 정상이다.

## 12. 마일스톤별 화면 구축 순서

도메인 모델 §11과 짝을 이룬다. **각 마일스톤의 완료 판정을 화면으로 옮긴 것**이다.

| # | 마일스톤 | 구축 화면 | 시연 경로 |
|---|---|---|---|
| **1** | 맞춤 취향을 남길 수 있다 | SCR-M0-01~04 · SCR-M1-01~09 · SCR-C-01~04 | 가입 → 온보딩 3스텝 → 마이 → 내 취향에서 다시 봄 |
| **2** | 친구에게 취향이 전달된다 | SCR-M2-01~07 | 링크 발급 → (다른 기기) 미리보기 → 가입 → 즉시 친구 → 상대 취향 열람 |
| **3** | 선물이 수령자 확인을 거쳐 결정된다 | SCR-M3-01~18 | 결제수단 등록 → 요청 → 동의 → 승인/대안 제시 → 자동 결제 → 실패 후 재시도 복구 |
| **4** | 고가 선물을 여럿이 함께 준비한다 | SCR-M4-01~08 | 펀딩 개설 → 참여 2명 → 달성선 넘김 → 차액 자동 결제 / 미달 전액 환불 |

### 마일스톤 경계에서 바뀌는 화면

| 화면 | M1~M2 | M3 이후 |
|---|---|---|
| SCR-M0-04 앱 셸 | 홈·친구·마이 3탭 (선물 탭 비활성) | 4탭 전부 |
| SCR-M1-06 마이 | 내 취향 · 초대 링크만 | 선물 내역 · 펀딩 내역 · 결제수단 추가 |
| SCR-M1-09 위시리스트 | 텍스트 입력만 | `( 카탈로그에서 고르기 )` 추가 (`product_id`) |
| SCR-M2-06 친구 상세 | `[ 선물 보기 ]` 숨김 | 버튼 노출 → SCR-M3-05 |
| SCR-M3-01 홈 | (M3에서 신설) | 승인 대기 · 진행 중 펀딩 |

- **M1~M2 단계에서 홈 탭은 SCR-M2-01(친구)이 대신한다.** 승인 대기도 펀딩도 없는 홈은 빈 화면이므로, M3 전까지는 친구 탭을 시작 화면으로 둔다.
- **빈 화면으로 연결되는 메뉴를 두지 않는다**는 원칙이 마일스톤 경계마다 적용된다. PRD의 "순서를 바꾸면 취향이 비어 있는 화면을 시연하게 된다"가 화면 노출 제어로 구현된다.

## 13. 갭과 열린 항목

이 문서가 화면을 그리면서 **근거 문서에 답이 없다고 확인한 것들**이다.

### 상위 문서에서 이미 열려 있던 것

| # | 항목 | 화면 영향 | 출처 | 언제 닫나 |
|---|---|---|---|---|
| 1 | **인증 방식** | SCR-M0-01·02의 버튼과 폼이 플레이스홀더 | 도메인 모델 §13-2 | M1 착수 직전 |
| 2 | **"반려" 대체 문구** | SCR-M3-12의 `( 다른 것도 좋아요 )` — 이 문서의 제안일 뿐 | PRD Constraints · 도메인 모델 §13-4 | M3 개발 중 |
| 3 | **대표 태그 3건 선정 규칙** | SCR-M2-01·M2-04 — 최신순을 전제함 | 도메인 모델 §13-5 | M2 착수 시점 |
| 4 | **캘린더의 위치** | SCR-M3-17을 **목록형으로 설계**. 월간 뷰 없음 | PRD Open Question · 도메인 모델 §13-3 | M3 착수 시점 |
| 5 | **PortOne 연동 상세** | SCR-M3-06의 위젯 영역이 비어 있음 | 도메인 모델 §12 | M3 착수 시점 |

### 이 문서에서 새로 발견한 것

| # | 갭 | 상황 | 제안 |
|---|---|---|---|
| 6 | **알러지 · 사이즈의 입력 자리가 없다** | PRD R9가 "알러지(건강), 사이즈(신체)가 한 프로필에 모인다"고 전제하지만, 도메인 모델에는 전용 필드가 없다. `TasteProfile.description` 또는 `TasteItem(unwanted)`로 흡수될 뿐이다 | MVP는 `description`으로 흡수하는 현 설계를 유지한다. 다만 **R9의 민감정보 전제가 `description` 자유 텍스트에 걸린다**는 점을 보안 검토에 반영해야 한다. 전용 필드가 필요해지면 `TasteItem.kind`에 `constraint` 값을 추가하는 경로가 가장 싸다 |
| 7 | **푸시 알림 없이 5분 TTL이 성립하지 않는다** | 알림이 인앱만이므로(도메인 모델 §5) 앱을 열지 않은 수령자는 `GIFT_RESPOND_TTL`(5분) 안에 응답할 방법이 없다 | 시연에서는 문제되지 않는다. 실서비스 배포 시 **TTL 상향 또는 푸시 도입 중 하나가 필수**임을 PRD의 "설정 가능해야 하며 실서비스 배포 시 조정"에 명시적으로 연결한다 |
| 8 | **기본 배송지가 없다** | D3 설계상 배송지는 거래마다 제공한다(SCR-M3-14). 선물을 받을 때마다 주소를 다시 입력해야 한다 | **의도된 비용으로 유지한다.** 프로필에 기본 배송지를 두면 관계 해제 후에도 주소가 남는 경로가 생겨 D3가 무너진다. 마찰이 크다고 판단되면 "직전 거래 주소 불러오기"(본인 데이터 복사)로 완화한다 |
| 9 | **추천 랭킹 규칙이 없다** | SCR-M3-05의 "취향에 맞을 것 같은 것"이 카테고리 일치 외의 신호를 쓸 수 없다. `description`은 자유 텍스트라 구조화되어 있지 않다 | MVP는 **카테고리 일치 + 가격대**로만 정렬한다. `description` 기반 추천은 데이터가 쌓인 뒤의 과제다. **PRD Evidence의 "가장 위험한 가정"(상세하게 기록할 의향)이 검증되기 전에는 정교한 추천을 만들 근거가 없다** |
| 10 | **상품 검색 방식 미정** | SCR-M3-03의 검색이 `Product.name` 대상이라는 것 외에 정의가 없다 | 시드 카탈로그 규모(수백 건)에서는 단순 `ILIKE` 부분 일치로 충분하다. 별도 검색 인프라는 과하다 |
| 11 | **데스크톱 · 태블릿 레이아웃 미설계** | PRD Constraints가 반응형을 요구하지만 이 문서는 모바일 와이어프레임만 그린다 | 하단 4탭 → 좌측 사이드바, 단일 컬럼 → 2컬럼(목록 + 상세)이 기본 변환이다. **SCR-M2-04(미리보기)만은 데스크톱에서도 단일 컬럼 중앙 정렬을 유지한다** — 링크를 PC에서 여는 경우가 많고, 이 화면의 목적은 전환 하나다 |
| 12 | **동시 요청 제한이 없다** | 같은 친구에게 여러 건의 `GiftRequest`를 동시에 보낼 수 있는지 도메인 모델에 제약이 없다 | 화면상 막지 않는다. 다만 SCR-M3-12에서 여러 건이 동시에 뜨면 수령자가 혼란스러우므로, **홈 카드는 `respond_due_at` 임박순 1건만 펼치고 나머지는 접는다** |
| 13 | **Pencil이 Pretendard를 렌더하지 못한다** | Pencil은 Google Fonts만 지원하고 시스템 설치 폰트를 읽지 않는다(`Malgun Gothic`·`Segoe UI`·`Arial` 전부 invalid로 확인). `.pen` 목업과 실제 앱의 한글 서체가 달라진다 | **의도된 차이로 유지한다.** `.pen`은 `Gothic A1`, 앱은 `next/font/local`로 Pretendard. 목업으로 자간·행간을 최종 판정하지 말 것 |
| 14 | **`.pen` 토큰이 두 벌 겹쳐 있다** | 구 토큰(`bg`/`forest`/`white`/`lime`/`coral`)과 신 토큰(`cream`/`green`/`sage`/`surface`/`accent`)이 공존하고, 텍스트 25개 중 19개가 한글 글리프가 없는 `Inter`를 참조한다 | §4.9의 목표 상태로 일괄 개명. 사용자가 작업 중인 파일이므로 **승인 후 실행** |

### 이 문서가 다루지 않는 것

| 항목 | 어디서 다루나 |
|---|---|
| 카피 최종안 | M3 개발 중 (갭 #2 포함) |
| 화면별 픽셀 단위 레이아웃 | §4의 토큰으로 구현 단계에서 확정 |
| 아이콘 세트 · 일러스트레이션 | 별도 조달 — §4는 아이콘의 색과 크기만 규정한다 |
| 스크린리더 라벨 문안 | 구현 단계 — 대비·포커스·터치 타깃 기준은 §4.8에 있다 |
| 다국어 | 범위 밖 |
| 관리자 도구 (`Category` · `Product` 시드 관리) | MVP 범위 밖 |
| 라우트 경로 설계 (`app/` 디렉터리 구조) | `/ecc:plan` — 구현 계획 |

## 14. 요약 — 이 문서가 확정한 것

| # | 결정 | 근거 |
|---|---|---|
| 1 | **온보딩은 3스텝, 그중 1스텝만 필수** | `onboarded_at` 조건이 SCR-M1-02에서 충족된다. 나머지는 skip 가능 |
| 2 | **미리보기 화면은 앱 셸 밖에 둔다** | R1의 방어선이 여기 하나뿐. 로그인 벽을 세우면 링크가 유통되지 않는다 |
| 3 | **미리보기는 가려진 항목의 *이름*을 보여준다** | 값은 숨기고 항목명은 노출하는 것이 전환 장치다 |
| 4 | **수령자 화면에 거절 버튼이 없다** | `declined` 상태가 없는 것의 UI 구현 |
| 5 | **재결제 동의는 별도 화면 + 금액을 숫자로 명시** | 약관 매몰이 아닌 구체적 동의 요건 |
| 6 | **`unwanted` 카테고리 상품은 선물하기 버튼을 비활성화** | 목록 필터만으로는 검색 우회를 막지 못한다 |
| 7 | **`have`는 목록에서 지우지 않고 표시만 바꾼다** | "이미 있다"와 "관심 없다"는 다른 신호다 |
| 8 | **추천 화면이 무엇을 걸러냈는지 밝힌다** | 조용한 필터는 빈약한 목록으로 읽힌다 |
| 9 | **대안 제시 고지에 차액 미청구를 함께 쓴다** | R6 완화 — 손해가 없다는 사실이 감정 비용을 낮춘다 |
| 10 | **펀딩 상세에 두 종류의 총액을 함께 표시** | 판정용(`paid`)과 캡 계산용(`reserved+paid`)이 다르다 |
| 11 | **개설자 = 수령자면 개설이 3스텝에서 2스텝이 된다** | 차액이 존재할 수 없으므로 동의 화면이 사라진다 (R3 해소) |
| 12 | **결제 실패는 일반 에러 화면을 쓰지 않는다** | 다음 행동이 정해진 실패는 전용 화면이 필요하다 |
| 13 | **마일스톤 경계마다 빈 화면으로 가는 메뉴를 숨긴다** | "취향이 비어 있는 화면을 시연하지 않는다"의 구현 |

### 비주얼 (§4)

| # | 결정 | 근거 |
|---|---|---|
| 14 | **시트론은 면으로만 쓰고, 화면당 하나만 둔다** | 레퍼런스 4장 전부가 노랑을 프레임·측면 필드로 쓴다. 작은 점으로 쓴 예가 없다 |
| 15 | **그 면은 화면 한쪽 모서리를 넘어 잘린다** | 모바일에는 둘러쌀 여백이 없다. 화면 밖으로 이어지는 면이 그 장치의 번역이자 이름(넌지시)의 실행이다 |
| 16 | **세리프는 숫자와 날짜에만 쓴다** | 한글 세리프는 14px 아래에서 무너진다. 넌지시에서 감정이 실린 값은 문장이 아니라 숫자다 |
| 17 | **타입 토큰은 라틴·한글 2종 스택으로 정의한다** | `Inter`·`Newsreader`·`Geist Mono`에 한글 글리프가 없다. 단일 패밀리로 두면 한글이 폴백으로 새어나간다 |
| 18 | **`coral`을 `alarm`으로 개명하고 실패·만료 전용으로 묶는다** | 크림 + 테라코타 액센트는 흔한 기본값이고, 레퍼런스에 그 색이 없다 |
